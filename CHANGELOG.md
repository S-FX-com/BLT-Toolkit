# Changelog

Release notes for BLT Toolkit, in the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format; versions follow [semantic versioning](https://semver.org/). CI bumps the version when a change merges to `main` (patch by default, `#minor` or `#major` in the merge commit message), and the plugin header, `BLT_TOOLKIT_VERSION` and the `readme.txt` stable tag always match. Requirement IDs refer to [SPEC.md](SPEC.md).

Nothing has been released yet. The merge that completes Phase 7 carries `#major` and publishes 1.0.0; until then everything is under **Unreleased**, summarized by module. The phase-by-phase record, with the evidence for each acceptance criterion, is in [tasks/todo.md](tasks/todo.md), and the reasons behind each decision are in [tasks/lessons.md](tasks/lessons.md).

## [Unreleased]

### Added

#### Plugin, settings and updates

- A single-site plugin for WordPress 6.3 and later and PHP 7.4 and later. Activation is refused on multisite with a readable notice, and on a network the plugin boots nothing (D1).
- Three modules, `switch`, `usernames` and `roles`, on shared services that always load (SPEC 4.1, BLT Secure's module pattern). Each can be switched off on **Overview** or **Settings > General**, or by `BLT_TOOLKIT_DISABLE_MODULES` (SEC-15); a module also stays off, with a **Conflict** badge naming the plugin to deactivate, while User Switching, Username Changer or User Role Editor is active (GEN-1). A module that is off loads no code beyond its registry entry; protection, the activity log, separate permissions, read-only enforcement and the part of switching that ends a switch on sign-in always run. Filter `blt_toolkit_modules`.
- Settings stored as one array merged over the SPEC 14.1 defaults and sanitized by hand, on save and again on read, so a value written outside the Settings screen means what the screen would have saved. Six tabs, each a link: General, Switching, Usernames, Roles, Activity log, Advanced.
- Updates from the plugin's GitHub releases through plugin-update-checker, checked every 24 hours and accepting only the `blt-toolkit-X.Y.Z.zip` release asset (a release without it, a tag or the branch is never offered). The optional read-only GitHub token comes from `BLT_TOOLKIT_GITHUB_TOKEN`, then the plugin's own option encrypted with the envelope copied from BLT Secure (libsodium, then OpenSSL AES-GCM, never unencrypted), then the shared BLT `github` group when the owner opts in. **Settings > Advanced** has **Test connection**, **Remove token** and **Check for Updates**; on a site where WordPress may not change files (`DISALLOW_FILE_MODS`) it says new versions arrive with the deployment and offers no update check.
- Schema: `{prefix}blt_toolkit_log` and `{prefix}blt_toolkit_snapshots` (SPEC 14.3), versioned by `blt_toolkit_db_version` and re-checked on admin screens, WP-Cron and WP-CLI, never on a visitor's page view.
- Capabilities (SPEC 5.1) granted to `administrator` on activation, after a baseline snapshot of the roles (SNAP-2), keeping any deny the owner set. If the tables or the baseline cannot be stored, activation is refused and no role is changed. Risk tiers (SPEC 5.4, `blt_toolkit_risky_caps`), the lockout-critical set (SEC-12, `blt_toolkit_lockout_critical_caps`) and who counts as an administrator (SPEC 5.2, `blt_toolkit_is_toolkit_admin`).
- Deactivation changes no data. Uninstall deletes nothing unless **Delete all plugin data on uninstall** is on; then it removes the tables, options, transients, user meta, job state, cron events, Action Scheduler actions, update-checker state, BLT Toolkit's own nine capabilities and the `blt_readonly_*` markers, and never a role, a role edit, another BLT plugin's capabilities or the shared BLT store (SPEC 14.6).
- Admin screens on the BLT design system: **Overview** (module cards, stat tiles, the setup card for legacy plugins and the recovery callout), **Roles** (also under **Users > Roles**), **Usernames**, **Activity**, **Tools** and **Settings**, each with its own capability (SPEC 13). Every screen works without JavaScript, at 420 px and by keyboard.

#### Protection

- The Guard (SPEC 5.3), enforced through `map_meta_cap`, `editable_roles` and BLT Toolkit's own write paths, so it holds for `users.php`, `user-edit.php`, `admin-ajax.php`, `admin-post.php`, REST and WP-CLI alike (SPEC 19, URE-1).
- A non-administrator can never edit, delete, remove, change the role of, rename or switch into an administrator (SEC-1), nor do any of that to someone with more capabilities than they have, including creating application passwords or sending password resets for them (SEC-2: `edit_user`, `delete_user`, `remove_user`, `promote_user`, `blt_switch_to_user`, `blt_change_username`). Superset comparisons leave out the deprecated `level_0` to `level_10` and treat read-only markers as restrictions (SEC-8). A capability check whose user argument is not a user ID fails closed.
- Grants and denies: a non-administrator may grant or deny only capabilities they hold, a role name is never accepted as a capability, and lifting a deny counts as a grant (SEC-3). Role dropdowns, the Users list's bulk change, user creation (including the default role) and the REST users endpoint offer only roles whose capabilities the person holds (SEC-4). Nobody changes their own roles or a role they hold, an empty REST `roles` list included (SEC-5), and a change to someone's roles is judged on the capabilities they will have afterwards.
- Administrators are hidden from everyone else in the Users list, its counts and the REST users collection, anonymous requests included (SEC-6, `blt_toolkit_hide_admins_from_non_admins`).
- Critical grants need a review and the role's name typed (SEC-10); every control shows its tier badge (SEC-11). The `administrator` role keeps its lockout-critical capabilities, cannot be deleted or renamed by ID, and its holders cannot be moved to another role (SEC-12); a save that would lock you out of the Roles screen is refused unless another administrator exists and you confirm (SEC-13).
- The `blt_switch_to_user` and `blt_change_username` meta capabilities (SPEC 5.1): switching and renaming never follow from `edit_users` (US-A, UC-3).
- Recovery mode: with `define( 'BLT_TOOLKIT_RECOVERY', true );` in `wp-config.php`, the next admin page an administrator opens snapshots the roles, gives the Administrator role back the lockout-critical capabilities and BLT Toolkit's own capabilities, and logs it; a notice stays until the line is removed (SEC-14). On a site that defines its roles in code, the repair holds for each request while the line is there, logged once a day.

#### Activity log

- One table for every switch, rename and role change (LOG-1), with the person who signed in as the actor and the account they were switched into as "acting as", from a switch chain rebuilt on the server from the session links; background jobs keep the chain of the request that started them (LOG-2). Rows BLT Toolkit writes by itself, such as a switched session it ended, are the system's (actor 0).
- Writes never block or interrupt the action they record; a failed write goes to the PHP error log and sets a flag that later successful writes stamp as recovered, never clear (LOG-3).
- A daily prune of entries older than **Keep entries for** (365 days) in batches of 1,000 (LOG-4, `blt_toolkit_log_retention_days`); IP addresses from `REMOTE_ADDR`, or `CF-Connecting-IP` only from Cloudflare's published ranges (LOG-5); `blt_toolkit_logged` receives each row as stored (LOG-6).
- The **Activity** screen (`blt_view_toolkit_log`): filters by module, action, who, acting as and date, each entry's details and role diff, and a CSV export of the filtered list. Exports and prunes are logged themselves.

#### Snapshots and background jobs

- A snapshot of the complete roles array before every roles write; a write whose snapshot cannot be stored is abandoned, except SEC-14 recovery, which goes ahead and records that the snapshot failed (SNAP-1). The newest 50 are kept (**Snapshots to keep**, `blt_toolkit_snapshot_retention`) plus the baseline and User Role Editor's imported backup, which are never pruned (SNAP-3). Canonical JSON, SHA-256 hashes and diffs (SNAP-5).
- Background jobs (SPEC 6.3) on WP-Cron with a loopback request, or Action Scheduler when present, time-boxed per tick (`blt_toolkit_tick_budget`), resumable, cancellable and retryable, with a live progress panel, rescue ticks when a tick dies, and the `blt-toolkit/v1/jobs/{id}` REST routes. Job types: `log_prune`, `username_bulk`, `role_reassign`, `count_no_role` and `legacy_uc_log` (JOB-5). `blt_toolkit_before_job` and `blt_toolkit_after_job`.

#### Switch

- Switch to another user and back, nested up to 10 levels, with User Switching's cookie mechanism under BLT names (`wordpress_blt_sw_*`, overridable with `BLT_TOOLKIT_SWITCH_COOKIE`, `BLT_TOOLKIT_SWITCH_SECURE_COOKIE` and `BLT_TOOLKIT_SWITCH_OLDUSER_COOKIE`; HttpOnly, SameSite=Lax). Switching back returns to the very session you switched from. **Switch Off** signs you out with a way back from the login screen and a fixed link on the site (SW-1 to SW-7, SW-17, SW-18).
- Permission is the `blt_switch_users` capability plus the protection rules, never `edit_users` (SW-1, D3). A link to a user who no longer exists says so (404) to someone who may switch and holds a link made for that user, and tells nobody else which user IDs exist (SW-4).
- Every link goes through the login URL with its own nonce, so it works with a custom login slug (BLT Secure) and is never page-cached; a second person switching into someone already switched into gets a warning first (SW-2, SW-8, SW-23). Redirects honor `redirect_to` and the public URL of a post, term, user or comment, core's `login_redirect` and `logout_redirect`, then `blt_toolkit_switch_redirect` (SW-9).
- A switched session ends with the session it came from, lasts at most 48 hours, and its cookies are browser-session cookies unless the person signed in with "Remember Me". A normal sign-in or sign-out, including a BLT M365 WP SSO sign-in, ends any way back, the sessions it could return to and the switched session that browser was in, also while the Switch module is off. Each switched session BLT Toolkit ends by itself is logged as **Switched session ended** (SW-5, SW-7, SW-10).
- Where switching appears: the Users list row action, the profile button, the toolbar ("Viewing as", "Switch back to", "Switch Off", and a "Switch to…" search over `GET blt-toolkit/v1/switch/users`), author archives, the notice after switching and the "not allowed" pages, the login screen, the Meta widget, the command palette, and the `blt_toolkit_switch_url` field on the REST `user` object (SW-12 to SW-20, SW-26, SW-27). Messages to the person who switched use their own language (SW-11).
- Every switch, switch back and switch off is logged (LOG-2). `blt_toolkit_switched_to`, `blt_toolkit_switched_back`, `blt_toolkit_switched_off`, `blt_toolkit_switch_redirect`, `blt_toolkit_switch_show_footer_link`, `blt_toolkit_switch_send_cookies` and `blt_toolkit_switch_search_limit`.
- **Work with tools made for User Switching** (on by default) also fires `switch_to_user`, `switch_back_user` and `switch_off_user` with User Switching's arguments and defines `current_user_switched()` when nothing else has (SW-19, D2).
- A **Support Agent** role, created from Settings > Switching after a preview of what it can do and whom it can switch into, and a typed confirmation (SW-21, SEC-10).
- WooCommerce: "Switch to customer" on the order screen (both order storages), "Switch back" in My Account and on WooCommerce's login form, and each person's cart and WooCommerce session kept apart across switch to, switch back and switch off (SW-22).
- Works with WordPress in its own directory (Bedrock): the toolbar, footer link, Meta widget, WooCommerce links, `current_user_switched()` and the log's attribution hold on the front end and REST too.
- Page caches: a signed-out page that shows the "Switch back" link is sent uncacheable, and the README explains the `wordpress_blt_sw_olduser_*` bypass (SW-25).

#### Usernames

- Change a username from the user's profile (a **Change username** section inside the profile form, moved into the Username row with JavaScript) and from the Users list, with live validation through `GET blt-toolkit/v1/usernames/check` and the same rules on the server for every path: length (1 to 60), characters, **Names that cannot be used**, `@`, names already taken and names equal to another user's email (UN-1 to UN-9, UN-16 to UN-19). Filters `blt_toolkit_validate_username`, `blt_toolkit_username_min_length` and `blt_toolkit_disallowed_usernames`.
- One rename procedure: by user ID, clearing both the old and the new user caches so the old username stops signing in at once on sites with Redis or Memcached, changing the author URL only when it was made from the old username (unique among users), and the display name and nickname only when they were the old username (UN-10, UN-13). Old author URLs redirect with a 301 (UN-13a). `blt_toolkit_before_username_change` and `blt_toolkit_after_username_change`.
- Renaming yourself keeps you signed in; renaming someone else signs them out everywhere when that setting is on; a warning comes first when the person is in a live switched session (UN-12, UN-14). An optional plain-text email (UN-15, `blt_toolkit_username_email`). Every rename is logged.
- Self-service: **Who can change their own username**, one toggle per role giving or taking `blt_change_own_username`, a **Wait between changes**, and **Ask for their current password** with a throttle of 5 wrong passwords in 15 minutes (UN-20 to UN-22, `blt_toolkit_username_password_throttle`).
- **Bulk rename from CSV** (UN-30): a template of every user you can see, an upload of up to 5,000 renames (`blt_toolkit_bulk_rename_max_rows`), a dry run of every row with chains ordered and swaps refused (D8), then a background job you can leave, cancel or retry. Each row is logged on its own.
- `[blt_toolkit_username_form]`: a front-end form for people allowed to change their own username, without JavaScript, with a theme-overridable template and the attributes `style` and `class` (UN-23).

#### Roles

- One role store for every BLT write to the roles option: only the capabilities that were on the page change (RO-1), a role changed since it was opened is refused with the difference (RO-2), a snapshot is taken and the option written once (RO-3), the Guard runs on the computed change set, and the diff is logged with the snapshot ID (RO-4). `blt_toolkit_before_roles_save` and `blt_toolkit_after_roles_save`. Opening a screen never writes a role (RO-5).
- The capability catalog (RO-10 to RO-14): core, content type, taxonomy and BLT Toolkit capabilities, and every capability found on a role or user; plain-English labels (`blt_toolkit_capability_labels`); one group per content type capability group, so a type that shares Posts' capabilities is shown inside Posts; plugin groups under **Plugins (detected)** from shared prefixes and `blt_toolkit_capability_groups` (WooCommerce's and Gravity Forms' declared while active); orphaned capabilities flagged, never removed automatically, with User Role Editor's grouped **From User Role Editor** (`blt_toolkit_orphan_family_labels`).
- **Advanced view** (`blt_edit_capabilities`): the matrix with the group tree, label, raw name, source and tier on every row, a toolbar of quick filter, Granted only, Show deprecated, Readable names and 1 to 3 columns, a sticky save bar, and review pages for Critical grants, lockouts and more than ten changes; **Add capability** and **Delete capability** for orphans only (RO-20 to RO-26).
- **Simple view** (`blt_edit_roles`): Basics, Content, Media and comments, Appearance, Plugins, Site, People, BLT Toolkit and a read-only "Other plugin permissions" summary. One content row per capability group with a level (No access, View, Contribute, Author (own only), Edit all, Full control) and the **Can delete** and **Manage {taxonomy}** modifiers, mapped by the pure `BLT_Toolkit_Simple_Mapper`; **Custom** and partly-on states that never change unless a state is picked; saves of only what changed; a review for Critical grants, replaced Custom rows and large changes; **Also allow** hints, announced to screen readers when a change shows them (SPEC 10, RS-1 to RS-17, Appendix A). `blt_toolkit_simple_controls`.
- **Separate permissions for a custom post type** (RS-30 to RS-35): a dry run, then one snapshot, one roles write and the users' own capabilities, so nobody's access changes on day one; the type gets its own row and levels, and **View** becomes read only in the dashboard, enforced with the `blt_readonly_{plural}` marker (RS-13, RS-14). **Share permissions again** reverts, with a separate cleanup of the unused capabilities. A notice and a warning row on the Plugins screen when another plugin overrides an isolated type or deactivation would revert it (RS-33, RS-34). `bricks_template` is excluded by default. `blt_toolkit_isolation_excluded_types`, `blt_toolkit_isolation_caps`, `blt_toolkit_post_type_isolated` and `blt_toolkit_post_type_shared`.
- Role lifecycle (RO-30 to RO-42): add a role from Blank, a WordPress default or a copy of a role you hold every capability of; rename; move users to a new role (the way to change an ID); delete with a replacement; merge; compare two roles; **Test as…** (X-3). People are moved by the `role_reassign` job. `blt_toolkit_role_created`, `blt_toolkit_role_deleted` and `blt_toolkit_role_renamed`.
- Role details: a description and **Hide the toolbar on the site** per role (SPEC 9.5, X-5).
- Users and profiles: **Additional roles** on the profile and Add New User (US-1), **Additional default roles** on every registration path (US-2), **Add role…** and **Remove role…** on the Users list (US-3), per-user capabilities with Inherit, Grant or Deny (US-10, US-11), and users without a role counted only on request, with a "No role (N)" view (US-12).

#### Tools

- **BLT Toolkit > Tools** (`blt_reset_roles`), five tabs, each previewed with the role store's own dry run, written only on confirm against the hash of the previewed roles, and snapshotted first; opening a tab writes nothing (RO-5).
- **Snapshots**: the list, a diff of each against today, and restore after a preview naming what Administrator keeps; the result links to undoing it (SNAP-4).
- **Export and import** (RO-44, RO-45): roles as `blt-toolkit-roles` version 1 JSON with their details and separate permissions; an import preview per role (New, Changed, Unchanged, Cannot be imported) with capabilities not registered on the site flagged, and Create, Merge capabilities, Replace capabilities or Skip per role, checked by the Guard.
- **Reset** (RO-43): built-in roles only, or a full reset to a fresh install's roles, each listing every change and the people left without a role first, and needing `RESET` typed.
- **Sync administrator** (RO-5): grants Administrator exactly the registered capabilities its preview lists.
- **Import from legacy plugins** (SPEC 15, also `manage_options`): Username Changer 3.3.1's settings, Allowed Roles (opt-in, since Username Changer never enforced them) and audit log (copied once, resumable, as a job above 1,000 rows); User Role Editor 4.66.2's other default roles, hide-admin-bar flags and first-activation backup, and removal of its `ure_*` capabilities after a dry run. The source plugins' data is only read; the ledger `blt_toolkit_legacy_imports` keeps a second run from duplicating anything.

#### Privacy and Site Health

- A personal data exporter and eraser for the activity log (SPEC 14.5), as "BLT Toolkit activity log" on WordPress's privacy screens. The export covers every row a person made, was switched into, is the object of, or is named in. The eraser keeps those rows as a security record, reports them as retained, blanks the person's logins in every row's details and their logins and display name in its summary, and blanks the stored username and IP only on rows they made; a long erasure carries its state across pages, the Activity screen's cached Who menu is dropped, and the erasure is logged (`toolkit` / `personal_data_erased`).
- Suggested privacy policy text: one "BLT Toolkit" section with the activity log and, while the Switch module runs, the switch cookies (SW-24). Settings > Activity log describes what the privacy tools do, with links to them.
- Five Site Health tests: the database tables (critical, with **Create the tables again**), plugins BLT Toolkit replaces that are active (GEN-1), separate permissions not in effect (RS-33, with a link to revert), recovery mode (SEC-14) and activity log write failures (LOG-3, with **Clear this warning**, which also saves a test entry). Both buttons are logged (`toolkit` / `tables_repaired`, `log_failure_cleared`). Privacy and Site Health load only on admin, cron and WP-CLI requests.

#### Development

- CI on every push and pull request: the syntax check on PHP 7.4 to 8.3, phpcs (WordPress-Extra, PHPCompatibilityWP), the unit tests on PHP 7.4, 8.2 and 8.3, the version-sync check, the POT drift check, and a release-zip build and verification. `release.yml`, ported from BLT Secure, runs the same checks on the merged commit before it bumps, tags and publishes `blt-toolkit-X.Y.Z.zip`.
- 601 unit tests against known vectors for the pure classes (SPEC 18), `bin/make-pot.js` and `languages/blt-toolkit.pot`, `bin/dev-site.sh` for disposable WordPress sites on SQLite.
- Documentation: `README.md`, `readme.txt`, `HOOKS.md` (every hook, matched to the code), `CLAUDE.md`, `AGENTS.md`, `tasks/todo.md`, `tasks/lessons.md`.

#### Not carried over from the source plugins

- Defects found by reading the source plugins are not reimplemented (SPEC 19): renames that leave the old login cached (UC-1), author URLs overwritten unsanitized (UC-2), renames authorized by `edit_users` alone (UC-3), length checked only in the browser (UC-4, UC-6), a case-sensitive disallowed list (UC-5), a form nested in the profile form (UC-8), renames by login (UC-9), signing yourself out when you rename yourself (UC-10), administrator protection that read only `$_GET` on two screens (URE-1), a capability list that wrote roles while rendering (URE-2), copies of roles more powerful than the person making them (URE-3), custom post types shown as independent while sharing Posts' capabilities (URE-4), saves that overwrote a concurrent change (URE-5), resets without an undo (URE-6), deletion of capabilities still in use (URE-7), and switching granted to anyone who can edit the target (US-A).
