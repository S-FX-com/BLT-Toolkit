# Changelog

Release notes for BLT Toolkit, in the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format; versions follow [semantic versioning](https://semver.org/). CI bumps the version when a change merges to `main` (patch by default, `#minor` or `#major` in the merge commit message), and the plugin header, `BLT_TOOLKIT_VERSION` and the `readme.txt` stable tag always match. Requirement IDs refer to [SPEC.md](SPEC.md).

The plugin is built phase by phase (SPEC 17). Entries under **Unreleased** have merged but not yet shipped in a release.

- **Phase 1: Guard, log, snapshots** (SPEC 17).
  - The Guard (SPEC 5.3): people who are not administrators can no longer edit, delete, change the role of, rename or switch into an administrator from any entry point (users.php, user-edit.php, admin-ajax.php, admin-post.php, REST, WP-CLI) (SEC-1), nor edit, delete, change the roles of or create application passwords for someone with more capabilities than they have (SEC-2), nor add or remove their own roles, including by sending an empty `roles` list to the REST users endpoint (SEC-5). A capability check whose user argument is not a user ID is refused for them. Role dropdowns, the Users bulk "Change role to", user creation and the REST users endpoint offer them only roles whose capabilities they hold, and a new user they create gets the site's default role only when they could give it (SEC-4). The `blt_switch_to_user` and `blt_change_username` meta capabilities (SPEC 5.1). Checks for later write paths: SEC-2, SEC-3 (grants and denies, role names refused as capabilities, lifting a deny counted as a grant), SEC-5, SEC-10, SEC-12 and SEC-13, with `can_change_user_caps()` for per-user capability edits.
  - Administrators are hidden from everyone else in the Users list, its role counts and the REST users collection, anonymous requests included (SEC-6, setting on by default; `blt_toolkit_hide_admins_from_non_admins`).
  - Recovery mode: with `define( 'BLT_TOOLKIT_RECOVERY', true );` in `wp-config.php`, the next admin page an administrator opens snapshots the roles, gives the Administrator role back the lockout-critical capabilities and every BLT Toolkit capability, and logs it; a notice stays until the line is removed (SEC-14). On a site that defines its roles in code, the repair holds for each request while the line is there, and the log and notice say so (one entry a day).
  - The activity log (LOG-1 to LOG-6): one table, actor and "acting as" attribution, IP recording with Cloudflare's ranges checked, writes that never block or interrupt the action they record, a daily prune of entries older than the retention in batches of 1,000, and `blt_toolkit_logged`, which receives the row as stored. The **Activity** screen filters by module, action, who, acting as and date, shows each entry's details and role diff, and exports the filtered list as CSV; exports and prunes are logged themselves.
  - Snapshots before every roles write (SNAP-1), kept newest 50 plus the baseline (SNAP-3, `blt_toolkit_snapshot_retention`), with listing, diff and restore logic for the Tools screen (SNAP-4). A roles write whose snapshot cannot be stored is abandoned, so activation is now refused in that case too; recovery mode alone goes ahead and records that the snapshot failed.
  - Background jobs (SPEC 6.3) on WP-Cron with a loopback request, or Action Scheduler when present, with `blt-toolkit/v1/jobs/{id}` REST routes, `blt_toolkit_before_job`, `blt_toolkit_after_job` and `blt_toolkit_tick_budget`. A tick that dies (a fatal error, a time limit) is taken over by a queued rescue tick, and the daily prune requeues any job that went quiet. Deactivation and uninstall clear the plugin's Action Scheduler actions as well as its cron events. The log prune is the first job.
  - Activation that gives the Administrator role a BLT Toolkit capability it lacked is logged, with the diff and the snapshot taken first. Restoring a snapshot no longer gives back a BLT Toolkit capability the owner had removed before it was taken; only a copy from before BLT Toolkit's first activation gets them all back.
  - Screens no longer say protection, hiding, recovery and the log are still to come.
- **Phase 2: Switch** (SPEC 17, SW-1 to SW-28).
  - Switch to another user and back, nested up to 10 levels, with User Switching's cookie mechanism under BLT names (`wordpress_blt_sw_*`, overridable with `BLT_TOOLKIT_SWITCH_COOKIE`, `BLT_TOOLKIT_SWITCH_SECURE_COOKIE` and `BLT_TOOLKIT_SWITCH_OLDUSER_COOKIE`; HttpOnly, SameSite=Lax). Switching back returns to the very session you switched from and ends the session made for the person you were viewing as. **Switch Off** signs you out with a way back from the login screen and a fixed link on the site (SW-1 to SW-7, SW-17, SW-18).
  - Permission is the `blt_switch_users` capability plus the protection rules, never `edit_users`: nobody but an administrator can switch into an administrator, and nobody can switch into someone with more capabilities than they have (SW-1, SEC-1, SEC-2). The deprecated `level_0` to `level_10` capabilities are now left out of that comparison, so a role built from named capabilities can switch into Subscribers; they still count when granting (SEC-3, SEC-8).
  - Every link goes through the login URL with its own nonce, so it works with a custom login slug (BLT Secure) and is never page-cached; a second administrator switching into someone already switched into gets a warning first (SW-2, SW-8, SW-23). Redirects honor `redirect_to` and the public URL of a post, term, user or comment, core's `login_redirect` and `logout_redirect`, then `blt_toolkit_switch_redirect` (SW-9). A normal sign-in or sign-out, including a BLT M365 WP SSO sign-in, ends any way back and the sessions it could return to, also while the Switch module is off (SW-10).
  - Where switching appears: Users list row action, profile button, toolbar ("Viewing as", "Switch back to", "Switch Off", a "Switch to…" search over the new `GET blt-toolkit/v1/switch/users` route), author archives, the notice after switching and the "not allowed" pages, the login screen, the Meta widget, the command palette, and the `blt_toolkit_switch_url` field on the REST `user` object (SW-12 to SW-20, SW-26, SW-27). Messages to the person who switched use their own language (SW-11).
  - Every switch, switch back and switch off is logged with who did it and whom they were acting as (LOG-2). `blt_toolkit_switched_to`, `blt_toolkit_switched_back`, `blt_toolkit_switched_off`, `blt_toolkit_switch_redirect`, `blt_toolkit_switch_show_footer_link`, `blt_toolkit_switch_send_cookies` and `blt_toolkit_switch_search_limit` are available (see `HOOKS.md`).
  - **Work with tools made for User Switching** (on by default) also fires `switch_to_user`, `switch_back_user` and `switch_off_user` with User Switching's arguments and defines `current_user_switched()` when nothing else has (SW-19).
  - A **Support Agent** role, created from Settings > Switching after a preview of what it can do and whom it can switch into, and a typed confirmation (SW-21, SEC-10).
  - WooCommerce: "Switch to customer" on the order screen (both order storages), "Switch back" in My Account and on WooCommerce's login form, and each person's cart and WooCommerce session kept apart across switch to, switch back and switch off (SW-22).
  - Privacy policy text about the switch cookies, and page-cache guidance for `wordpress_blt_sw_olduser_*` in the README (SW-24, SW-25). A signed-out page that shows the "Switch back" link is sent uncacheable.
  - A switched session is signed out as soon as the session it was switched from ends, and lasts at most 48 hours whatever "Remember Me" gave the person who switched; the switch cookies are browser-session cookies unless they signed in with "Remember Me" (SW-5, SW-7). Switch cookies that no longer validate, or that belong to someone else's session in the same browser, are ignored and expired (SW-10, SEC-9).
  - Works with WordPress in its own directory: the toolbar, footer link, Meta widget, WooCommerce links, `current_user_switched()` and the log's "acting as" read the old-user cookie and the server-side session links, so they hold on the site's front end and REST requests too, and the stack cookie also reaches a login slug outside the WordPress directory (SW-2, SW-17, LOG-2).
  - The original user's row, profile and REST field offer "Switch back" rather than a nested switch; Switch Off is refused on a full stack instead of dropping the person who signed in; the "Viewing as" toolbar item links to the profile, with switching back on its child item (SW-5, SW-6, SW-12, SW-14).
- **Phase 3: Usernames** (SPEC 17, UN-1 to UN-30).
  - Change a username from the user's profile: a **Change username** section inside the profile form (no form of its own), which with JavaScript moves into the Username row behind a **Change** button and checks the name as it is typed through `GET blt-toolkit/v1/usernames/check`. The profile save checks the name on the server whatever the browser did, then renames; the next screen says what changed. The Users list gets a **Change username** row action (UN-16 to UN-19).
  - The rename is one procedure for every path: permission is `blt_change_usernames` for someone else and `blt_change_own_username` for yourself, never `edit_users`, with the protection rules (nobody but an administrator renames an administrator, nobody renames someone with more capabilities than they have). It updates by user ID, clears both the old and the new user caches, so the old username stops signing in at once on sites with Redis or Memcached, changes the author URL only when it was made from the old username (with core's algorithm, unique among users), and changes the display name and nickname only when they were the old username (UN-10, UN-13).
  - Old author URLs redirect to the new one with a 301 (setting on by default); a username a current user has always wins (UN-13a).
  - Renaming yourself keeps you signed in on the same session; renaming someone else signs them out everywhere when **Sign the person out everywhere** is on. A warning, with a box to tick, comes first when the person is in a switched session that is still live (UN-12, UN-14). Two renames of the same user at the same moment cannot both go through, so the wait between self-service changes holds (UN-21).
  - Optional plain-text email to the renamed person through `wp_mail()`, with the subject and message from Settings > Usernames and the `blt_toolkit_username_email` filter (UN-15). `blt_toolkit_before_username_change` and `blt_toolkit_after_username_change` are available. Every rename is logged with the old and new username.
  - Settings > Usernames: **Who can change their own username**, one toggle per role that gives or takes the `blt_change_own_username` capability (a snapshot first, checked by the protection rules, logged), plus the wait between changes and the optional current-password check (UN-20 to UN-22).
  - **Bulk rename from CSV** on the Usernames screen (UN-30): download a template of every user you can see (`user_id,username,new_username`, written so it uploads back unchanged), upload it with new usernames (UTF-8 with or without a byte order mark, commas or semicolons, CRLF or LF, up to 5,000 rows with a new username, `blt_toolkit_bulk_rename_max_rows`; rows left empty are skipped, so a full template uploads back on a site with more users than that; a file over the upload limit, or with more than 100 columns in a row, is refused with the reason), and check a dry run of every row before anything changes: Ready, Error with the reason, or No change, with warnings for your own account, a switched session that will end and an author URL that will change. Chains run in the right order (`bob` to `carol` before `alice` to `bob`); swaps such as `alice` to `bob` and `bob` to `alice`, and two rows claiming one name, are refused. Starting asks for a backup acknowledgment once per sign-in, pins the email (and its text), sign-out and author URL settings for the whole run (the author URL rule is the one the dry run used), and runs the renames as a background job with a live progress panel that keeps going when the tab is closed, can be cancelled (finished rows stay renamed) and offers **Retry failed**. Only the person who started a bulk rename, or an administrator, can follow, cancel or retry it, and a cancel or retry is logged with who did it. Each row is logged on its own, and a row whose user was renamed since the dry run is left alone. Works without JavaScript. **Recent changes** lists the usernames activity, or only your own if you cannot view the activity log.
  - Background jobs keep the switch chain of the request that started them, so log rows written by a bulk rename started while switched name the person who signed in, acting as the account they switched into (LOG-2).
  - `[blt_toolkit_username_form]`: a front-end form for people allowed to change their own username, posting to `admin-post.php` and returning to the same page with the result, without JavaScript. It renders nothing for visitors and people without the permission, tells someone in their wait period when they can change it again, asks for the current password and the switched-session confirmation when those apply, and loads its stylesheet only where a styled form renders (`style="styled|none"`, `class`). Its markup is a template a theme can override at `your-theme/blt-toolkit/username-form.php` (UN-23).
  - The username rules' filters `blt_toolkit_validate_username`, `blt_toolkit_username_min_length` and `blt_toolkit_disallowed_usernames` are available; the bulk dry run's "author URL will change" warning predicts the exact slug, uniqueness suffix included. Uninstall with data deletion on also removes the per-user dry runs and result notices.

  - Role metadata (SPEC 9.5): a description and **Hide the toolbar on the site** per role, applied only when every one of a user's roles has it; a switched user keeps the "Switch back" link at the foot of the page (X-5).
  - Users and profiles: **Additional roles** on the profile and Add New User (US-1), **Additional default roles** on every registration path, set in Settings > Roles (US-2), **Add role…** and **Remove role…** on the Users list (US-3), per-user capabilities with Inherit, Grant or Deny in the Roles screen's user mode, linked from a **Capabilities** section that replaces WordPress's "Additional Capabilities" row (US-10, US-11), and users without a role counted only on request, cached for an hour, as the `count_no_role` job on large sites, with a "No role (N)" view (US-12).
  - `blt_toolkit_risky_caps`, `blt_toolkit_capability_labels` and `blt_toolkit_capability_groups` are now read. A role lifecycle page you may not open answers 403. Uninstall with data deletion on also removes the Roles screen's and the Users list's per-user result notices.
- **Phase 5: Simple view and separate permissions** (SPEC 17, RS-1 to RS-35, Appendix A).
  - **Simple view** on the Roles screen (`blt_edit_roles`): Basics, Content, Media and comments, Appearance, Plugins, Site, People, BLT Toolkit and a read-only "Other plugin permissions" summary, in SPEC 13.2 order, each control with its tier badge (SEC-11). Content shows one row per content type capability group, labeled with every member (RS-10), with a level (No access, View, Contribute, Author (own only), Edit all, Full control) and the **Can delete** and **Manage {taxonomy}** modifiers, mapped to capabilities by the pure `BLT_Toolkit_Simple_Mapper` (SPEC 10.3, 10.4). WordPress's default roles read as SPEC 10.4 says for Posts and Pages (RS-16). A row that matches no level reads **Custom** and a partly granted toggle reads partly on; neither changes unless a state is picked, and then the review lists what is removed (RS-4, RS-15).
  - Saving submits only the controls that changed, works out each one's adds and removes within its own capabilities on the server, and writes through the role store with context `simple` (RS-5, RO-1 to RO-3). The review (RS-6) runs as a dialog with JavaScript and as its own page without it, for Critical grants (typed role name, SEC-10), changes of more than ten capabilities and replaced Custom rows. Dependency hints with **Also allow** (RS-7, RS-17). The Simple and Advanced tabs remember each person's choice and ask before leaving unsaved changes (RS-1, RS-2). **Edit in Advanced** opens the matrix narrowed to one control (`ctl`), and the matrix names each capability's Simple control (RO-21). Types on site-wide capabilities read "Controlled by" the control that owns them, `map_meta_cap` false types "Custom ownership rules" (RS-11, RS-12). "Hide the toolbar on the site" and "Change their own username" are in Simple view (SPEC 9.5, X-6).
  - A Simple save needs `blt_edit_roles` and an Advanced save also `blt_edit_capabilities`, checked by the role store itself (`BLT_Toolkit_Role_Store::context_cap()`, SPEC 9.3, 10.7).
  - **Separate permissions for a custom post type** (RS-30 to RS-35, `blt_edit_capabilities` and `manage_options`): a dry run of the capabilities each role and each user with Posts or Pages capabilities of their own receives, so effective access is unchanged on day one (denies included), then one snapshot (`before_isolation`), one roles write, the users' own capabilities, a log row and `blt_toolkit_post_type_isolated`. The `register_post_type_args` filter added by the main file applies it on every request and returns at once when nothing is isolated (RS-31, `blt_toolkit_isolation_caps`). **Share permissions again** reverts (`blt_toolkit_post_type_shared`), with a separate dry-run cleanup of the unused capabilities (RS-32). Verification at `init` priority `PHP_INT_MAX` shows a notice and switches off the row's levels when another plugin overrides an isolated type (RS-33); the result is kept in the new autoloaded option `blt_toolkit_isolation_state` for the Site Health test. A warning row under BLT Toolkit on the Plugins screen says what deactivating changes (RS-34). `bricks_template` is excluded by default (`blt_toolkit_isolation_excluded_types`, RS-35).

Capabilities stay additive: another role at a higher level lifts it.

  - `blt_toolkit_simple_controls`, `blt_toolkit_isolation_excluded_types`, `blt_toolkit_isolation_caps`, `blt_toolkit_post_type_isolated` and `blt_toolkit_post_type_shared` are available (see `HOOKS.md`). Uninstall with data deletion on also removes `blt_toolkit_isolation_state`.
  - Review fixes. The read-only marker `blt_readonly_{plural}` is a restriction, not a power: a role manager no longer needs it to manage a View-level user or role or to grant View, while taking it away (removing it, or denying it to a user) counts as giving editing back and needs the type's editing yourself (SEC-2, SEC-3, SEC-8, RS-14). Someone held read-only on a type no longer counts as holding its `edit_{plural}` against people who can edit. Manage {taxonomy} appears only for term capabilities of the taxonomy's own, never the type's publish capability or another type's (SPEC 10.3). "Enforced by BLT Toolkit" and the View help text follow what View really grants. RS-33 now also checks `create_posts` and the other strings separate permissions give a type, so a plugin update that turns read-only enforcement off is reported; a registration's `do_not_allow` overrides are kept, other overrides stop isolation and are reported. Damaged or imported entries for core types, invalid names or core capability strings are never applied or stored. Reverting is checked by the Guard for non-administrators, as isolating is. While an isolated type's plugin is inactive, its capabilities are no longer offered for deletion as orphans, and Simple view lists the type with a way to revert. A damaged state option no longer breaks the cleanup page. A Simple save that changes only "Hide the toolbar" is checked like Role details. The review dialog starts at its heading, is described by its summary and saves on Enter; "Edit in Advanced" asks to save or discard first; repeated controls name their content type to screen readers. Only a small part of separate permissions loads on a visitor's page view (SEC-9).
- **Phase 6: Tools** (SPEC 17, SNAP-4, RO-5, RO-43 to RO-45, SPEC 15, SPEC 13.2). **BLT Toolkit > Tools** (`blt_reset_roles`) has five tabs, each a link: Snapshots, Export and import, Reset, Sync administrator and Import from legacy plugins (also `manage_options`). Every tab previews with a dry run of the role store, so what the preview shows (diff, the Guard's verdict, the Critical capabilities that need a typed role name under SEC-10) is what the write does; opening any tab writes nothing (RO-5), and a confirm carries the hash of the roles its preview was made from, so roles changed in between write nothing.
  - **Snapshots** (SNAP-4): the list, newest first and paged, with time, who, why, and how many roles and capabilities differ from today; each can be viewed as a diff and restored. A restore shows its diff first, names what Administrator keeps beyond the snapshot (the SEC-12 lockout set, and BLT Toolkit's own capabilities when the snapshot predates them), then takes a `before_restore` snapshot and writes once through the role store under the Guard (context `restore`, log `snapshot_restored`). The result notice links to the restore of the snapshot just taken, which undoes it.
  - **Reset** (RO-43): built-in roles only (Administrator, Editor, Author, Contributor and Subscriber get WordPress's default capabilities back, names kept, custom roles untouched) or a full reset to exactly what a fresh install creates (custom roles deleted, with their user counts and a warning when the default role disappears). Each lists every change first, needs the typed word `RESET`, takes a `before_reset` snapshot, writes once (context `reset`, log `roles_reset`) and re-grants BLT Toolkit's capabilities to Administrator.
  - **Sync administrator** (RO-5): the registered capabilities Administrator lacks (never orphans, deprecated or multisite-only capabilities, read-only markers or meta capability names; a deny on Administrator is listed and kept), granted on confirm, exactly the list shown (context `sync`, log `administrator_synced`). Needs the Roles module, whose capability catalog it reads; Snapshots and Reset work with that module off.
