# Lessons

Gotchas found while building, and decisions recorded with their reasons (including every **Should** in `SPEC.md` that is not followed, and every SPEC and `DESIGN.md` conflict, per `CLAUDE.md`). Append only; never rewrite history. Newest at the bottom.

## 2026-10-21: Phase 0 decisions

- **The repository and the update checker point at different places; owner to confirm.** The repository currently lives at `github.com/sfxdotcom/BLT-Toolkit`, but SPEC 3 names `S-FX-com/BLT-Toolkit`. The update checker in `blt-toolkit.php` points at `https://github.com/S-FX-com/BLT-Toolkit/`, as SPEC 3 says, so releases must be published there (or the repository transferred there) before installed sites can find them. Until then the Phase 0 criterion "a second release updates a test site through the updater" cannot pass. CONVENTIONS 17, item 8 records the same `sfxdotcom` versus `S-FX-com` question for BLT Secure.
- **Vendored files come from BLT Activity Log, which matches BLT Secure; BLT Events has drifted.** `assets/css/blt-design-system.css` and plugin-update-checker (`includes/lib/plugin-update-checker/`, v5p7) were vendored from BLT Activity Log and match BLT Secure byte for byte (checked with `sha256sum` and `diff -r`; the stylesheet's SHA-256 starts `72ea81f0`), as do `DESIGN.md`, `CONVENTIONS.md`, `includes/blt-family/`, `blt-family-smoke.php` and `assets/img/`. BLT Events carries a drifted `blt-design-system.css` (Events-specific rules such as `.blt-badge-trash`, `.blt-review-reason` and the solid status badges) and an older update checker (v5p6). That is family drift to resolve in the canonical copy and port to every repo in one pass (CONVENTIONS 16.3, rule 3), not here.
- **Version 0.1.0 while phases are built; 1.0.0 comes from `#major`.** The header, `BLT_TOOLKIT_VERSION` and the `readme.txt` stable tag stay at 0.1.0 while the phases are built, and nobody bumps them by hand. CI bumps patch by default, so the first release after a merge publishes 0.1.1. Put `#major` in the message of the merge that completes Phase 7 to publish 1.0.0.
- **Uninstall removes only BLT Toolkit's own capabilities, not "every `blt_*` capability".** SPEC 14.6 says uninstall "removes every `blt_*` capability". Read literally, that would also strip other BLT plugins' capabilities from roles and users (`blt_view_activity_log` from BLT Activity Log, `blt_manage_documents` from BLT Documents) and break those plugins. `uninstall.php` therefore removes only the nine capabilities in SPEC 5.1 and the `blt_readonly_*` markers. This follows the intent of SPEC 14.6 and CONVENTIONS 11 ("never delete things the plugin does not own").
- **SPEC 21 decisions D1 to D14 are adopted as recommended unless the owner overrides them; D4 and D14 still need confirmation.** D4 (menu placement): a top-level BLT Toolkit menu whose submenus carry their own capabilities, plus Users > Roles. `DESIGN.md`'s admin menu example registers one entry under `manage_options` at position 58, CONVENTIONS 6.1 describes "one menu entry, one capability", and the family's menu position is still open (CONVENTIONS 17, item 16: Documents uses 81, the `DESIGN.md` snippet 58). D14 (front-end prefix): `.blt-tk-*` and `--blt-tk-*`, pending confirmation of BLT Tube's prefix. Both are listed under "Open decisions" in `tasks/todo.md`.

## 2026-10-21: Phase 0 build

### Core services

- **The update token is resolved on `init` (priority 1), not on `plugins_loaded`.** `BLT_Family::get()` runs `__()` through `BLT_Family_Groups`, and before `init` that calls `determine_locale()` / `get_user_locale()`, which authenticates the current user early, before SSO plugins add their `determine_current_user` filters. Every request path of the update checker (`admin_init`, cron events, WP-CLI) comes after `init`, so nothing is lost.
- **The update checker variable is not a PHP global under WP-CLI.** WP-CLI loads plugin files inside a function scope. Do not rely on `$GLOBALS['blt_toolkit_update_checker']` outside HTTP requests.
- **`grant_admin()` adds only capabilities the `administrator` role does not mention, and keeps an explicit `false` (deny).** Reactivating must not undo a deliberate owner edit; SEC-14 recovery is the way back from a damaged administrator role. SPEC 5.1 says "granted on activation" without covering explicit denials, so this is a recorded interpretation.
- **`grant_admin()` takes `Snapshots::take( 'before_save' )` before it writes (SNAP-1).** On first activation that snapshot is skipped as a duplicate of the baseline taken a moment earlier, so a fresh activation leaves exactly one row.
- **`blt_toolkit_lockout_critical_caps` can add capabilities but never shrink the SEC-12 base set, because that set is the anti-lockout guarantee.** `blt_toolkit_risky_caps`, by contrast, fully replaces the tier lists, since tiers are a classification. Tier entries may end in `*` as a prefix wildcard (`edit_others_*`), and Critical wins over Elevated.
- **BLT Secure's crypto rejects an AES-GCM envelope of exactly 28 bytes (empty plaintext) as tampered (`<= 28`).** Our copy uses `< 28`, with a unit test. Consider porting the fix to BLT Secure and the other `*_Crypto` copies.
- **`Settings::save_tab()` takes the tab's fields flat, keyed as in the group (General uses the module keys).** A missing toggle is false; a missing or invalid non-toggle keeps the stored value; integers are clamped (`min_length` 1 to 60, `cooldown_days` 0 to 365, `snapshot_retention` 1 to 500, `retention_days` 1 to 3650). These ranges are our choice; SPEC gives only defaults.
- **The disallowed-usernames list is stored lowercased**, through `sanitize_user()` (non-strict) and `strtolower()` as core does, because UN-4 compares case-insensitively on both sides.
- **`role_meta` entries that carry no information (empty description, toolbar shown) are dropped on write** to keep the autoloaded option small. Role IDs are sanitized to `[A-Za-z0-9_-]` with case preserved, so they still match existing roles.
- **`github_token_status()` reports `undecryptable` ahead of `shared`**, so the Advanced tab asks for the plugin's own token again even while a shared token is in use. A decrypt failure never deletes the envelope (a read never writes), so restoring the old salts brings the token back.
- **Deactivation and uninstall clear cron by scanning `_get_cron_array()` for hooks prefixed `blt_toolkit_`**, so hooks added in later phases are covered without updating a list. The update checker removes its own cron on deactivation; uninstall clears `puc_cron_check_updates-blt-toolkit` and `external_updates-blt-toolkit` explicitly.
- **`BLT_Toolkit_Plugin::is_active()` means "booted on this request"**, so it is false on multisite, before `plugins_loaded` priority 1, and in the activation request. Use `module_status()` for the configured state.
- **Settings writes start from the request-start copy of the option.** Two admins saving different tabs at the same moment could overwrite each other's group. Acceptable for Phase 0; RO-2-style locking may be wanted for `role_meta` and `isolated_post_types` in Phases 4 and 5.
- **`Snapshots::take()` returns 0 and calls `error_log()` on failure but does not block the write.** Phase 1 decides whether a failed SNAP-1 snapshot must stop a roles write.

### Tooling and CI

- **Composer run as root in a non-interactive session disables plugins**, so `dealerdirect/phpcodesniffer-composer-installer` never registers WPCS (`phpcs -i` lists only PEAR, PSR, Squiz and Zend) and `composer <script>` aborts. In the cloud dev container, run `COMPOSER_ALLOW_SUPERUSER=1 composer lint|phpcs|test`, and after a fresh install either run `vendor/bin/phpcs --config-set installed_paths` with the absolute paths of `vendor/phpcompatibility/*`, `vendor/phpcsstandards/*` and `vendor/wp-coding-standards/wpcs`, or install with `COMPOSER_ALLOW_SUPERUSER=1`. CI runs as a non-root user and is unaffected.
- **The family release pipeline (BLT Secure, BLT Activity Log) runs `git tag vX` (lightweight) then `git push --follow-tags`, which pushes only annotated tags** (confirmed in a throwaway repo), so the tag was really being created by `softprops/action-gh-release` through the API at the default branch head. BLT Toolkit's `release.yml` commits, rebases, creates an annotated tag, then runs `git push origin main refs/tags/vX`. It also builds and verifies the zip before pushing, so a tree that cannot be packaged never gets a version commit or tag, then rebuilds after the push so the asset matches the tagged commit.
- **`release.yml` keeps everything BLT Secure's does that BLT Activity Log dropped**: the explicit greps of the header, `BLT_TOOLKIT_VERSION` and the Stable tag at the new version. They run alongside `check-version-sync.sh`.
- **BLT Activity Log's `build-zip.sh` rsyncs `./` into `build/` without excluding `build/`**, which can ship an empty `build/` folder inside the zip. BLT Toolkit has `/build` in `.distignore`, passes `--exclude=/build` to rsync, and `verify-zip.sh` fails on a `build/` folder.
- **POT drift check: the CI release bump changes the header version without regenerating the POT, and the copyright year changes on January 1.** BLT Activity Log's check (which ignores only `POT-Creation-Date`) would fail the next PR. BLT Toolkit also ignores the `Project-Id-Version` and `# Copyright` lines, and fails when the POT is untracked, because `git diff --quiet` passes for untracked files.
- **`make-pot.js` deviates from BLT Activity Log's, each time to match `wp i18n make-pot`:** it sorts by path, then numeric line, comparing code units (Activity Log's `localeCompare` is locale-dependent, so CI and laptops could disagree and report false drift); it attaches translators comments placed earlier in the same statement, in block, docblock or `//` style (Activity Log missed the common `/* translators */` line followed by `printf( esc_html__( ... ) )`); it extracts `wp.i18n.*` calls in JS and skips comments inside argument lists; and it writes the plugin header strings, merged with a matching string in the code. Intended differences from WP-CLI: `$obj->__()` method calls and concatenated literals are not extracted (WPCS rejects concatenation anyway).
- **PrefixAllGlobals matches prefixes with `stripos( ... ) === 0`, so listing `current_user_switched` as a prefix whitelists that one function name without excluding its file.** Do not whitelist `switch_to_user`, `switch_back_user` or `switch_off_user` the same way: that would also allow declaring `switch_to_user()`, which GEN-2 forbids. The SW-19 compat `do_action()` calls need an inline `// phpcs:ignore WordPress.NamingConventions.PrefixAllGlobals.NonPrefixedHooknameFound -- SW-19 compat: User Switching's action name.` instead.
- **WordPress-Extra includes `Universal.Files.SeparateFunctionsFromOO`**, so the `current_user_switched()` shim (SW-19) must live in a functions-only file, inside a `function_exists()` guard, that the switch module requires explicitly, not inside a class file.
- **`bump-version.php` has no ABSPATH guard on purpose**: it is a CLI script that runs without WordPress and never ships (`.github` is excluded from the zip). The "every PHP file" rule is about plugin files. It keeps the `@package Blt_Toolkit` docblock. `tests/test-bump-version.php` is BLT Activity Log's test, renamed.
- **Every downloadable SQLite Database Integration release (2.1.13 and later) declares "Requires at least: 6.4".** The `db.php` drop-in loads it without activating it, and WordPress 6.3 installs and runs with 3.1.1 (verified). `BLT_SQLITE_VERSION` can pin another release.
- **The shared `blt-site stop PORT` uses `pkill -f "php -S localhost:PORT"`, a prefix match, so `stop 890` would also kill a server on 8903.** The helper generated by `bin/dev-site.sh` adds a trailing space to the pattern. Reusing a site NAME with Redis on would read the old database's cached objects, so the drop-in uses a per-install, per-database prefix with `WP_REDIS_SELECTIVE_FLUSH`, and `blt-site new` flushes that site's keys when `BLT_OBJECT_CACHE=redis`.
- **The dev container has no rsync, so `build-zip.sh` falls back to its own copy**, which supports root-anchored `/path` patterns and bare names or globs, and fails on any other `.distignore` pattern shape. CI keeps BLT Activity Log's rsync invocation. Only the fallback has been run locally.
- **Commit `.github/scripts/*.sh`, `bin/dev-site.sh` and `bin/make-pot.js` with mode 100755**, as BLT Activity Log does; `bump-version.php` and the workflows are 100644. Run `node bin/make-pot.js` right before committing so `languages/blt-toolkit.pot` matches the final strings.

### Admin screens

- **Menu position 81 (D4; CONVENTIONS 17, item 16).** BLT Secure registers its top level at 81 and the shared BLT family screen (`BLT_Family_Admin`) at 80; CONVENTIONS 17 says Documents uses 81 too. BLT Events has no top-level page of its own (its menu is its CPT, with `menu_position` null). 81 keeps the family's menus together just below Settings, and WordPress shifts a taken position by a fraction, so two plugins on 81 coexist.
- **Users > Roles (D4) is `add_users_page()` with the menu slug `admin.php?page=blt-toolkit-roles` and no callback.** WordPress prints the slug as a plain href and registers no second page, so `get_admin_page_parent()` still resolves to `blt-toolkit` and the BLT Toolkit menu is the one highlighted on the Roles screen. For a user without `edit_users`, `add_users_page()` files the link under Profile; that is expected.
- **Per-submenu capabilities under a `manage_options` top level work as SPEC 13.1 wants.** Verified with a user holding only `read` and `blt_edit_roles`: WordPress repoints the top-level link to the first submenu they can reach (Roles), and the page's hook suffix stays `blt-toolkit_page_blt-toolkit-roles`, so gating assets on the hook `add_submenu_page()` returned still works. Never hard-code hook suffixes: they derive from `sanitize_title()` of the translated menu title.
- **`wp_nonce_field()` gives the input an `id` equal to its name, so a screen with several forms repeats that id.** `BLT_Toolkit_Admin::form_fields()` prints the hidden action and nonce inputs by hand, with no id. `check_admin_referer()` needs only the nonce.
- **Settings > Advanced puts Test connection and Remove token inside the token card as `<button form="...">` pointing at two small standalone forms printed after the main form.** That gives separate POSTs, no nested forms and no JavaScript. Pressing Enter in the token field still submits the main form, because buttons that belong to other forms do not count as its default button.
- **Overview module cards use the selectable-card styling on a `<div>`, with a `.blt-toggle` inside as the control, rather than the catalog's label-plus-hidden-input form.** DESIGN 2 says to toggle `.is-selected` with JS, and the plugin ships no admin JS in Phase 0. Here `.is-selected` is server-rendered and means "this module is running now", while the toggle shows the saved setting. Nesting a toggle label inside a label card would be invalid HTML.
- **Should-level deviation from the catalog: `nicename_policy` (Usernames) and `default_view` (Roles) are `<select>`s, not radio selectable cards.** Without JS a selectable card's hidden radio gives no visible feedback until save. Revisit when the plugin ships an admin script.
- **PRG notices carry only a whitelisted code plus integer or `sanitize_key()` arguments (`http`, `via`, `err`), never message text.** Unknown codes render nothing. Notices print with the `inline` class so core's script does not move them above the page header.
- **`route_post()` checks the POST method (405), then the action's capability (403), then the nonce.** A delegated user posting to a settings action gets "You do not have permission to do that." even with a junk nonce, and nothing is written.
- **`github_token_status()` decrypts the stored token, so `Settings::render()` calls it only on the Advanced tab.** Test connection sends the token only as an `Authorization: Bearer` header; the redirect carries the HTTP status and the token's source (`constant|stored|shared|none`), never the token.
- **To render a screen in the `conflict` or `disabled` state without touching the shared WordPress core** (an mu-plugin there would leak into every agent's site), run `blt-site wp NAME --exec='class user_switching {} define("BLT_TOOLKIT_DISABLE_MODULES","usernames");' eval-file render.php`. `--exec` runs before plugins load, so GEN-1 detection and SEC-15 both see it.
- **In this sandbox, `wp_remote_get()` to api.github.com from the dev server receives HTTP 403 from the agent proxy.** Verify the Test connection branches with a `pre_http_request` mock, plus a `wp_redirect` filter that throws so the handler's `exit` is skipped. In PHP test harnesses, beware that a `'404'` array key becomes the integer 404.

### Verification

- **Never run `wp plugin uninstall blt-toolkit` on a dev site:** `wp-content/plugins/blt-toolkit` is a symlink to the repo and WP-CLI deletes the plugin directory. Test uninstall by deactivating, then `blt-site wp NAME eval 'define( "WP_UNINSTALL_PLUGIN", "blt-toolkit/blt-toolkit.php" ); include "/home/user/BLT-Toolkit/uninstall.php";'`. Deactivation already clears the `blt_toolkit_*` and update-checker cron events, so re-add some before uninstalling to prove uninstall clears them too.
- **To verify "no front-end queries", run `php -S` with a scratch router that defines `SAVEQUERIES` and dumps `$wpdb->queries` with caller chains on shutdown,** then compare against the same requests with the plugin inactive. The SQLite drop-in records callers, so BLT frames can be grepped directly, and no mu-plugin goes into the shared core.
- **A `php -S` router runs in WordPress's global scope, so its own variables must not be named `$wp`, `$path` or anything else WordPress uses as a global.** A router that set `$wp` broke every request with "Call to a member function add_query_var() on string".
- **`pkill -f "php -S localhost:PORT"` also matches the shell that runs it when the same command line contains that text, and kills it (exit 144).** Stop a server from a compound command with an exact match instead: `ps -eo pid,args | awk '$2=="php" && $3=="-S" && $4=="localhost:PORT" {print $1}' | xargs -r kill`.
- **`wp core multisite-convert` writes the multisite constants into `wp-config.php`, which every dev site shares.** Use `--skip-config`, then pass the constants per process: `--exec='define( "MULTISITE", true ); …'` for WP-CLI and a `php -S` router that defines them for HTTP. With that, SQLite Database Integration 3.1.1 runs a real network (network admin, per-site and network activation), so D1 was verified on SQLite.
- **Over HTTP, the multisite refusal answers 500 with the `wp_die()` page while carrying the `Location: plugins.php?error=true…` header that `activate_plugin()` set before running the hook.** Browsers and `curl -L` do not follow `Location` on a 5xx, so the person sees the readable message and its Back link; the plugin is not recorded as active.
- **WordPress 6.3 on PHP 8.3 logs core's "Calling get_class() without arguments is deprecated" (`class-wp-http.php` line 329) on every `WP_Http` request**, including at install and login before BLT Toolkit is active. It is not a BLT Toolkit notice, and SPEC pairs 6.3 with PHP 7.4, where it does not fire. Read a 6.3 debug log with that line in mind.

## 2026-10-21: Phase 0 review fixes

- **`enableReleaseAssets( $regex )` alone still installs source archives.** Its default, `Api::PREFER_RELEASE_ASSETS`, offers a release's `zipball_url` when no asset matches, and even `REQUIRE_RELEASE_ASSETS` alone only makes that release count as none, after which plugin-update-checker's GitHub strategies fall back to the newest tag's zipball and then the branch. A release can lack its asset for real: `softprops/action-gh-release` creates the release before it uploads, and anyone can make a release by hand. `blt-toolkit.php` passes `REQUIRE_RELEASE_ASSETS` and keeps only the `latest_release` strategy through `$checker->addFilter( 'vcs_update_detection_strategies', ... )` (the filter `puc_vcs_update_detection_strategies-blt-toolkit`). This deviates from the BLT Secure (`includes/class-updater.php`) and BLT Activity Log (`blt-activity-log.php`) copies, which share the gap; port both lines to them in one family pass (CONVENTIONS 16.3, rule 3). Consequence to know: a release whose upload failed offers no update until the zip is attached to it.
- **CI did not run on `main`, and `release.yml` had no quality gate, so a red tree could be bumped, tagged and shipped.** `ci.yml` had `branches-ignore: main` (copied from BLT Activity Log) and nothing makes a merge wait for pull request checks. `release.yml` now runs `composer lint`, `composer phpcs`, `composer test` and the POT drift check before "Bump version", and `ci.yml` runs on every push, `main` included. The release's POT check runs `git checkout` on the POT afterwards, because the bump step's `git commit -am` would otherwise commit the regenerated creation date. BLT Activity Log and BLT Secure share the gap.
- **`wp option patch update` stores strings, so a setting read with PHP truthiness means the opposite of what was typed.** `"false"` and `"off"` are truthy, and `uninstall.php` used `empty()`, so `delete_data_on_uninstall` set to `false` from WP-CLI deleted everything. `BLT_Toolkit_Settings::merge()` now sends every stored value through `sanitize_field()`, with the default standing in for "the current value" (`read_field()`): booleans through `to_bool()`, integers clamped by `INT_RANGES`, whitelists applied, lists cleaned (which also stops a damaged `usernames.disallowed` from crashing Settings > Usernames). `uninstall.php`, which cannot load the plugin, repeats `to_bool()` inline; keep the two in step. Never read a BLT setting from the raw option with `empty()` or `(bool)`; use `BLT_Toolkit_Settings::get()`.
- **Screens name idle modules from the registry, never by building them.** `BLT_Toolkit_Admin::modules()` used to `new` every module that did not boot just to read `label()`, which loaded code SPEC 4.1 says must not load (and would let a broken module file break the screens used to diagnose it, SEC-15). The built-in names and descriptions now live in `BLT_Toolkit_Plugin::labels()`, which the module classes return too; a new built-in module adds its entry there. A filter-added module that is not running shows its key. The earlier "Also check" verification ran only on requests that render no screen, so it missed this; verify "not loaded" while the screens render.
- **`module_status()` reports `conflict` before `disabled`.** GEN-1 requires the Overview card to name the legacy plugin to deactivate, and the constant's note ("remove it from that constant") was false while the legacy plugin was active. When both apply, the conflict note also names the constant.
- **Correction to "The four Phase 0 filters were flipped to Available" (Docs and migration, above).** Only `blt_toolkit_modules` is applied by a running code path. `blt_toolkit_is_toolkit_admin` and `blt_toolkit_lockout_critical_caps` are Planned (Phase 1) and `blt_toolkit_risky_caps` Planned (Phase 4), with a note that the function applying each already exists. A hook is Available when something calls it, not when the method that would apply it exists.
- **Correction to "PRG notices carry only a whitelisted code plus integer or `sanitize_key()` arguments" (Admin screens, above).** `sanitize_key()` still lets a link spell out words (`err=your-site-is-compromised_call-…`), and `http=200&via=stored` faked a successful Test connection. The result is now carried with `blt_sig`, a nonce whose action contains the values (`BLT_Toolkit_Admin::result_args()`), so only the person who ran the test sees it and no value can be changed. Every other notice code takes no argument.
- **Activation refuses, before touching any role, when the tables or the baseline cannot be stored.** Granting first would let the next activation's baseline record BLT Toolkit's own grants as the "before" state. Every refusal goes through `refuse_activation()`, which also clears `puc_cron_check_updates-blt-toolkit`: loading the main file for the activation already built the update checker, whose `Scheduler` constructor schedules that event at once, and no deactivation hook ever runs for a plugin that never became active. The multisite refusal left that event behind before.
- **The baseline race is closed by inserting, then keeping the oldest baseline.** No lock is held, so nothing can be left stuck. The oldest is always a true "before" copy: each activation stores its baseline before it grants, so a copy read after any grant was inserted after that activation's own, older, baseline.
- **`maybe_upgrade()` runs only on wp-admin screens (not admin-ajax.php), WP-Cron and WP-CLI, and checks that before reading the version option.** When the version was never stored, the option is not in the autoloaded set, so `get_option()` alone is a query on every request, before any retry of dbDelta. Any WP-CLI command runs `maybe_upgrade()`, so `blt-site wp NAME eval …` repairs a schema broken on purpose; break it, then test over HTTP.
- **WP-CLI's `--exec` runs before WordPress loads, so `add_filter()` does not exist there.** Pre-initialize the hook instead: `$GLOBALS['wp_filter']['query'][10]['my_id'] = array( 'function' => $callback, 'accepted_args' => 1 );`, which WordPress turns into a `WP_Hook`. Put it in a file and `require` it from `--exec` or from a `php -S` router, to fail a CREATE or INSERT during activation, or to hold an INSERT for a race test, without an mu-plugin in the shared core.
- **Until Phase 1 lands, screens say protection, hiding, recovery and the log are still to come.** A control that has no effect yet stays on its form, marked with `BLT_Toolkit_Admin_Settings::later()` or a "Coming soon" badge, because `save_tab()` reads a toggle that is not submitted as off. Phase 1 has a todo item to restore the present tense.
- **Docs quote the screen's label, with the settings key, not SPEC's name for the setting.** HOOKS.md and the README's Settings table say **Work with tools made for User Switching** (`switch.compat_hooks`), mentioning SPEC's "Compatibility hooks" only in passing; likewise the uninstall toggle is **Delete all plugin data on uninstall** on the screen and everywhere else.

## 2026-10-22: Phase 1 (Guard, log, snapshots, jobs)

### Decisions and owner questions

- **Decided policy: no snapshot, no roles write.** A BLT write to the roles option is abandoned with a `WP_Error` when its SNAP-1 snapshot cannot be stored (`Snapshots::take()` returned 0). The one exception is SEC-14 recovery, which goes ahead (an administrator who is locked out must get back in), logs the row with status `warning` and `snapshot_failed: true`, and writes a line to the PHP error log. `Caps::grant_admin()` follows the policy too, so an activation whose `before_save` snapshot fails is refused like one whose baseline fails, before any role changes (verified on `p1verify`).
- **`level_*` capabilities stay strict (owner to confirm).** SEC-8 compares them like any other capability, so a custom role without `level_0` cannot manage Subscribers: a manager role built without it could not promote a subscriber (SEC-2) and did not see Subscriber in its editable roles (SEC-4); adding `level_0` fixed both. Kept strict because legacy plugins still check `level_N`. Ignoring levels in `BLT_Toolkit_Superset::normalize()` would be a one-line change.
- **Owner question, SEC-2 scope.** SEC-2 covers `promote_user`, `blt_switch_to_user` and `blt_change_username`, as SPEC 5.3 words it. A non-admin with `edit_users` can therefore still change the email or password of, or delete, a more powerful non-admin such as an editor, which is a takeover path. Adding `edit_user`, `delete_user` and `remove_user` to the Guard's `$subset_checked` list would close it.
- **Owner question, hiding administrators from anonymous REST requests.** SEC-6 hides administrators from every non-admin, and an anonymous visitor is one, so the public `/wp/v2/users` no longer lists administrator authors. `blt_toolkit_hide_admins_from_non_admins` receives `WP_User` 0 for visitors and can opt out.
- **Hiding works by the `administrator` role.** If `blt_toolkit_is_toolkit_admin` widens who counts as an admin, those extra users are protected by SEC-1 but not hidden.
- **Stricter than the wording of SEC-4:** `editable_roles` always drops `administrator` for non-admins, even one holding every admin capability. `check_role_change()` also applies SEC-2 to roles, as RO-4 lists: a non-admin cannot edit a role whose capabilities exceed theirs, nor `administrator` at all.
- **Only core's `time` counting strategy is replaced** (the one `get_views()` uses). On sites with more than 10,000 users core skips counting, and only the Administrator view is dropped.
- **Core quirks the Guard does not change.** `users.php?action=delete` still shows core's confirmation page (with the admin's login) for an administrator target, because core checks `delete_user` only at `action=dodelete`, which is refused with 403. `user-edit.php` refusals answer HTTP 500, because core's `wp_die()` there passes no status.
- **No helper for US-1/US-3 yet.** Those write paths (Phase 4) should combine `get_editable_roles()`, `Guard::can_act_on_user()` and a check that the actor is not changing their own roles (SEC-5).
- **The job runner landed in Phase 1, not Phase 3.** LOG-4 prunes as a `log_prune` job (JOB-5), so `BLT_Toolkit_Jobs` and the `blt-toolkit/v1/jobs` REST routes ship now, and `blt_toolkit_before_job`, `blt_toolkit_after_job` and `blt_toolkit_tick_budget` are Available. The prune's inline fallback (when `Jobs::start()` returns a `WP_Error`) stays. A cursor job's `process` is called as `$process( $state, $pinned )` so the by-reference `$state` survives; `call_user_func()` would lose it.
- **A log retention below 1 day keeps every row** instead of deleting everything (only reachable through `blt_toolkit_log_retention_days`; Settings clamps 1 to 3650), so a filter returning 0 cannot wipe the audit trail. This matches BLT Activity Log's pruner.
- **The log records its own exports and prunes** (`toolkit/log_exported` with the entry count and filters, `toolkit/log_pruned` with the count and cutoff), so taking out or removing audit records is itself on the record.
- **The Overview's recovery callout (SPEC 13.2) replaces the Guard's recovery notice on that one screen**, so it is not said twice; every other admin screen shows the notice while `BLT_TOOLKIT_RECOVERY` is set.
- **Known gaps handed to Phase 7.** The LOG-3 failure flag (`blt_toolkit_log_failure`) is not cleared by later successful writes, so Site Health should compare its `time` or offer `clear_failure()`. If the log table goes missing while `blt_toolkit_db_version` is current, the Activity screen's reads print wpdb errors under `WP_DEBUG_DISPLAY` (writes are protected; `maybe_upgrade()` checks only the version). Privacy (SPEC 14.5): `details` hold logins in `switch_chain` and whatever modules record (old and new usernames), so the eraser must blank those as well as `actor_login` and `ip`, and the exporter should match the user inside `switch_chain`; `acting_as_id` has no index in the SPEC 14.3 schema, so those queries scan the table. Activity rows per page are fixed at 50 (a `per_page` URL argument of 1 to 200 is honored); there is no Screen Options setting.

### WordPress and PHP gotchas

- **`php -S` (the cli-server SAPI) uses opcache even though `opcache.enable_cli` is Off**, because that setting only covers the `cli` SAPI, and `revalidate_freq` is 2. A router include rewritten within 2 seconds of the last request is served stale, so a constant it defines seems to do nothing. Sleep 2 seconds after rewriting, or switch behavior with flag files the router tests with `is_file()`, so the router itself never changes.
- **`wp-admin/includes/menu.php` refuses a user who cannot reach the screen before `admin_init` fires.** SEC-14 recovery therefore runs on `init` with `is_admin()` and refreshes the current user with `get_role_caps()`, so the same request loads even after the administrator role lost `read` (verified: `read`, `manage_options` and `blt_edit_roles` removed, `/wp-admin/` answered 200 with the dashboard).
- **Every `current_user_can()` runs the `map_meta_cap` filter.** A static-method array callable costs about 0.2 microseconds more per call than a closure (call_user_func_array with a class lookup), so the Guard registers a closure gate. A callback at its own priority level costs about 0.1 microseconds more than sharing an existing one.
- **The SQLite drop-in hooks `map_meta_cap` at priority 10** (`sqlite_plugin_map_deactivation_capability`), so dev-site benchmarks always have one callback in the baseline.
- **Core's `count_users()` has no cache and runs on every users.php load.** To correct the counts when hiding admins, return core's own query plus `meta_value NOT LIKE '%"administrator"%'` from `pre_count_users`: it replaces the query instead of adding one, and core then leaves out the Administrator view itself. Do not parse the view HTML as User Role Editor does.
- **`WP_User::get_role_caps()` merges roles in the order of the capabilities meta**, so a later role's `false` overrides an earlier `true`. SEC-13 simulation and the per-request cache keys must keep that order.
- **Anonymous `GET /wp/v2/users` can list a user with no posts of their own**, because the block theme auto-creates a published `wp_navigation` post authored by them. It is not a leak.
- **Never use `action` as a GET filter name on an `admin.php?page=` screen:** `wp-admin/admin.php` fires `do_action( "admin_action_{$_REQUEST['action']}" )`, and the same name on an admin-post.php form replaces the route's own `action` field. The Activity screen uses `log_action`.
- **Current WordPress (7.1 checked) renders a `WP_List_Table` primary cell as `<th scope="row">`, not `<td>`.** Core's mobile CSS hides every cell after `.column-primary` until a JavaScript row toggle opens it, so a no-JS override must not name the element: `.blt-ui.blt-toolkit-activity .wp-list-table tr:not(.inline-edit-row):not(.no-items) .column-primary ~ td:not(.check-column) { display:block }`.
- **With `WP_DEBUG_DISPLAY` on, wpdb prints a failed query into the page**, which can break a redirect that follows. `$wpdb->suppress_errors( true )` stops that, but it also stops wpdb's own `error_log` line, so the caller must log the error itself (`BLT_Toolkit_Log::fail()`).
- **`json_encode()` with `JSON_PARTIAL_OUTPUT_ON_ERROR` past the depth limit returns valid JSON with the deep branch silently dropped** (`json_last_error()` is `JSON_ERROR_DEPTH`). Check `json_last_error()` rather than the return value.
- **WordPress 7.1 spawns WP-Cron on `shutdown`** (`wp_cron()` adds `_wp_cron` there), so every WP-CLI command and every admin page sets the `doing_cron` lock for 60 seconds. A `GET /wp-cron.php` made right after a WP-CLI call therefore runs nothing (it sees the fresh lock and returns), and passing `?doing_wp_cron=` without the matching transient does nothing either. To test a cron event over HTTP: run inspection commands with `--exec='define( "DISABLE_WP_CRON", true );'`, delete the `doing_cron` transient the same way, then request `/wp-cron.php` with no query string.
- **A non-blocking loopback to the single-threaded `php -S` server still runs:** the job runner's admin-ajax.php request is queued until the current request ends, then served, so the `log_prune` job finished one second after the cron request that started it.
- **Admin requests read two non-autoloaded options for the update token on every page** (`blt_toolkit_secrets`, `blt_family_opt_in`, through `Settings::github_token()` on `init`). That is Phase 0 behavior, constant per request and never on the front end; noted for the SEC-9 review.

## 2026-10-22: Phase 1 review fixes

### Decisions

- **SEC-2 now covers `edit_user`, `delete_user` and `remove_user` (supersedes the "Owner question, SEC-2 scope" above).** Core maps the application-password capabilities (`create_app_password` and the rest), session sign-out and the password-reset link to `edit_user`, so a delegated user manager could mint an application password for a more powerful non-admin (an Editor, a holder of `blt_edit_roles`) and sign in as them over REST or XML-RPC, silently: the impersonation SPEC 5.1 and SPEC 19 (US-A) rule out. Reproduced, then closed (201 before, 403 after). Consequence: a user manager can no longer edit or delete anyone whose capabilities exceed theirs. Cost: about 1 µs per guarded check for the cached comparison (`tasks/todo.md`, SEC-9). The owner can narrow it again by taking the keys out of `BLT_Toolkit_Guard::$subset_checked`, but application passwords would then need their own rule.
- **A key named like a role is never a capability for a non-admin, whatever its value.** `WP_User::get_role_caps()` counts every key of the `{prefix}capabilities` meta that names a role as a membership, so `administrator => false` makes the user an administrator. `can_grant()` refuses role names among denies too, and per-user edits go through the new `can_change_user_caps()`, which also refuses removals of role keys and one's own capabilities (SEC-5). `can_act_on_user()` still lets a user act on themself, because switching and renaming have their own self rules; it is not the per-user capability check.
- **Denies are checked like grants, and lifting a deny is a grant (SEC-3).** A non-admin may deny only capabilities they hold, and removing a key whose current value is `false` (in a role or in a user's meta) is checked as granting it, because the holders get it back from their other roles. Flipping `false` to `true` was already refused; deleting the same key was not.
- **No non-admin deny in a role an administrator also holds (SEC-1, extended).** A later role's `false` overrides the `true` of `administrator`, so an administrator given a second role (URE's "other roles" does this on the sites we replace) could lose `manage_options` and the rest of the lockout set through a role a delegated role editor may edit. Refusing denies there was chosen over refusing every edit of such a role: a grant or a removal cannot take anything from an administrator, whose own role keeps the lockout set (SEC-12). "Holds" is one `get_users( role => array( 'administrator', $role ), number => 1 )` query, run only when a non-admin's save denies something; like SEC-6 hiding, it goes by the administrator role, so users made toolkit admins by `blt_toolkit_is_toolkit_admin` alone are not seen.
- **Owner question, SEC-14 scope.** Recovery inspects only the `administrator` role's own capabilities, as SPEC 5.5 words it ("changes nothing else"). It cannot repair an administrator locked out by a `false` in another role they hold, or by a per-user deny in their own meta: `recover()` finds nothing missing. Since this review a non-admin can no longer cause that through BLT Toolkit, but an administrator, another plugin or WP-CLI still can. Should recovery also check each administrator's effective capabilities, and report (or lift) such denies?
- **SEC-4 also covers the default role.** Core asks `editable_roles` only for a role that was chosen; with no role in the request (always, for a creator without `promote_users`, whose form has no Role field) it gives `default_role`. A non-admin's user creation is refused when that role is not one they may give: `user_profile_update_errors` covers user-new.php and admin-ajax.php `add-user` (both run `edit_user()`), and `rest_request_before_callbacks` covers `POST /wp/v2/users` (`rest_pre_insert_user` cannot refuse: `create_item()` casts its result to an array). Anonymous self-registration is untouched, and a default role that does not exist grants nothing, so it is allowed. US-2's additional default roles need the same check in Phase 4.
- **An empty REST `roles` list needs `promote_user`.** `update_item_permissions_check()` asks for `promote_user` only when `roles` is non-empty, yet `prepare_item_for_database()` empties the roles whenever the key is set, so `{"roles":[]}` removed every role with `edit_user` alone, also on `/users/me` for any user (SEC-5). The Guard's REST hook matches the controller method the route resolved to (`update_item`, `update_current_item`, `create_item` of a `WP_REST_Users_Controller`), not the URL, because REST routes match case-insensitively and can be spelled more than one way.
- **Guarded checks fail closed on a target that is not a user ID.** `'1abc'`, `true`, `array( 1 )` and negative numbers became 0 (no target, core's mapping) in the Guard, but `(int)` or `absint()` turn them into an administrator's ID in a caller. For a non-admin they now get `do_not_allow`; a missing argument and `0` still mean "no target".
- **Restoring a snapshot re-adds BLT Toolkit's capabilities only when the snapshot predates them (SNAP-4).** `restorable_roles()` used to add every BLT capability the snapshot's administrator did not mention, so a snapshot taken after the owner removed `blt_switch_users` gave it back. Now they are added only when the snapshot's administrator mentions none of them (the baseline, or any copy of the state before the first activation); the SEC-12 lockout set is still always forced. Phase 6's preview must name what the restore adds beyond the snapshot.
- **`grant_admin()` logs its write** as `toolkit` / `administrator_synced`, with the granted capabilities, a `Role_Diff::diff()` and the `before_save` snapshot ID (the baseline's ID on a first activation, where that snapshot is skipped as a duplicate). A reactivation that gives back a capability the owner removed is now on the Activity screen.
- **`blt_toolkit_logged` receives the details as stored** (the stored JSON decoded: the truncation marker, substituted values, the switch chain), and an empty array when there are none, matching HOOKS.md's "the row as written".
- **The Activity screen's filter menus are cached** in the transient `blt_toolkit_log_menus` with the highest row ID they cover. A view reads `MAX(id)`, then only newer rows (with a 100-row overlap for late commits) and merges them (`BLT_Toolkit_Log::merge_menus()`, unit-tested); the prune drops the transient when it deletes rows, and the Phase 7 eraser must too (`forget_menus()`). Chosen over an index on `acting_as_id`, which would change the SPEC 14.3 schema. The unused `distinct_actions()`, `distinct_actors()` and `distinct_acting_as()` were removed.
- **Recovery of roles defined in code repairs in memory and logs once a day.** With `$wp_user_roles`, nothing can be saved, so each admin request repairs the role again; the snapshot is skipped (no write to snapshot before), and the transient `blt_toolkit_recovery_in_code`, keyed by the set granted, keeps the `warning` row to one a day instead of a "success" row per request. The notice says the roles live in code.
- **Background jobs recover by themselves (JOB-1).** A tick that takes the lock replaces whatever is queued for the job with a rescue tick at the moment the lock would go stale (`rescue_at()`: lock time plus `lock_stale_after()` plus 5 s); `dispatch()` replaces the rescue with an immediate tick and `finish()` clears it. A tick that finds the lock busy queues one when nothing is queued. The daily prune calls `resume_stalled()`, which requeues any live job quiet for longer than a lock may be (covering a job orphaned by deactivation), and starts no second prune while one is live. Deactivation calls `Jobs::unschedule_all()`, and `uninstall.php` unschedules `blt_toolkit_job_as_tick` itself.
- **Settings > Activity log no longer claims privacy-tool coverage**; it is a "Coming soon" line until Phase 7 ships the exporter and eraser.

### WordPress, PHP and browser gotchas

- **`wp_schedule_single_event()` refuses an event with the same hook and arguments within ten minutes of one already scheduled, in either direction**, so moving a job's tick earlier or later means `wp_clear_scheduled_hook()` first. WP-Cron takes an event off the schedule before running it, so the running tick's own event is never cleared by mistake.
- **Action Scheduler counts the action it is running as in progress, not pending**, so `as_unschedule_all_actions()` from inside that action cancels only the queued ones, and `as_has_scheduled_action()` sees only those. A PHP fatal inside an action leaves it failed, never retried: the rescue action is what carries the job on.
- **A real mid-tick fatal for tests:** a `query` filter (pre-initialized in `$GLOBALS['wp_filter']` from a router include, or from WP-CLI `--exec='require ...'`) that calls `set_time_limit( 1 )` and spins on the first `DELETE` of the log table, removing its flag file first so it fires once. `max_execution_time` counts CPU time on Linux, so the spin hits it in about a second, in `php -S` and in WP-CLI alike.
- **`isset( $request['roles'] )` on a `WP_REST_Request` is true for `[]` and false for `null`**, the same test core's `prepare_item_for_database()` uses, so the Guard's REST hook matches core exactly.
- **`edit_user()` ignores a posted `role` when the actor lacks `promote_users`**, and user-new.php does not show the Role field to them, so every user they create gets `default_role`.
- **A grid of labels and values inside a table-layout: fixed cell needs `minmax(0, …)` tracks.** `minmax(8em, max-content) 1fr` gave the `<dd>` zero width at 800 to 1024 px and let six nested levels spill across the next three columns at 1280 px. `fit-content(40%) minmax(0, 1fr)`, with the details body and every `<dd>` as `container-type: inline-size` and an `@container (max-width: 26em)` rule that stacks label over value, keeps every level inside its cell; `overflow-wrap: break-word` (not `anywhere`) keeps words whole where they fit. Between 783 and 1279 px the fixed em widths of When, Who, Module and Status become percentages, so What happened keeps about half the table.
- **`WP_List_Table` sortable columns take a fifth element since WordPress 6.3** (`array( 'when', true, '', '', 'desc' )`): the column the default view is sorted by, so its header carries `sorted desc` and `aria-sort`, and the first click sorts the other way.
- **A visible label plus screen-reader text in one translatable string**: `__( 'Details<span class="screen-reader-text"> of entry %d</span>', … )` through `wp_kses()` with only `span[class]` allowed, so translators can reorder the whole phrase; likewise "Role added: %s", "Failed: %s" and "Warning: %s", shared with the job panel's script.
- **`as_unschedule_all_actions( $hook, array(), $group )` does not cancel "all"**: with empty arguments it takes the hook-only or group-only shortcut only when the other one is empty, and otherwise cancels actions whose arguments are exactly `[]`. Every job tick carries its job ID, so the review's suggested call (and the original `unschedule_all()`) left every tick queued after deactivation and uninstall. Cancel by hook alone (`as_unschedule_all_actions( 'blt_toolkit_job_as_tick' )`); the hook is BLT Toolkit's own.
- **A `wp action-scheduler run` killed by a fatal error leaves its claim behind**, and the next run answers "There are too many concurrent batches" until Action Scheduler's cleaner releases it (minutes later); pass `--force` in tests.

## 2026-10-22: Phase 2 (Switch)

### Decisions

- **SEC-8 comparisons leave out `level_0` to `level_10` (decided policy; supersedes "`level_*` capabilities stay strict" under Phase 1).** SPEC 17 Phase 2 criterion e requires the SW-21 Support Agent (`read`, `list_users`, `blt_switch_users` exactly) to switch into Subscribers, who hold `read` and `level_0`, so a strict comparison makes the SPEC's role and its criterion incompatible. `BLT_Toolkit_Superset::normalize()` keeps the levels; `is_subset()` and `missing()` skip them (`is_level()`); the new `missing_grants()` counts them, and the Guard's SEC-3 `can_grant()` uses it, so a non-admin still cannot grant or deny a level they do not hold. - **`blt_switched_from_session` holds the sha256 verifier of the actor's token (the key core stores the session under in `session_tokens`), not the token.** User Switching stores the raw token in the target's session; a raw token in user meta is half of a working cookie for the actor. Nothing reads the field back to authenticate: switching back takes the token from the signed stack entry.
- **The stack keeps at most 10 entries (`BLT_Toolkit_Switch_Cookies::MAX_DEPTH`).** An 11th nested switch is refused with "You have switched too many times in a row. Switch back first." (403); `push()` also drops the oldest beyond 10. An entry is about 140 bytes, so a full stack stays near 1.4 KB, well under the 4 KB browsers accept.
- **The switch row is logged just before the identity changes**, so `acting_as_id` is the user switched from and the chain ends with them; `HOOKS.md` says so (it said "at the same point as `blt_toolkit_switched_to`"). The compat `switch_to_user` receives the real token of the target's new session where User Switching passes `''`, and the target's session is destroyed right after `blt_toolkit_switched_back`, as User Switching does after `switch_back_user`.
- **SW-21 asks for the typed role name (SEC-10) and needs `blt_create_roles` as well as `manage_options`.** `blt_switch_users` is Critical, so creating a role that holds it is a Critical grant; adding a role is what `blt_create_roles` is for (SPEC 5.1). The confirmation ignores case and surrounding spaces. Creation takes a `before_save` snapshot first (no snapshot, no write) and logs `switch/role_created` with the diff. `blt_toolkit_role_created` is not fired yet, because its arguments are still proposed (Phase 4).

Without it, WooCommerce deletes the admin's stored session on the first signed-out request, and on switch back the guest's cart replaces the admin's. The guest session created while switched off (a `t_` row) is left for WooCommerce's own expiry cleanup.

The switch module now also clears the cookies on `blt_m365_sso_user_authenticated` (verified with Microsoft mocked). Other SSO plugins that skip `wp_login` have the same gap; User Switching has it too.
- **A normal `wp_login` over a switched browser clears the switch cookies but leaves the target's switched session in `session_tokens` until it expires**, as User Switching does.
- **SW-24's privacy text lives in `BLT_Toolkit_Switch::privacy_policy()`**, not in `class-blt-toolkit-privacy.php` as `tasks/todo.md` planned; Phase 7 should merge it with the log's text into one policy section.

Recorded as open in `tasks/todo.md`.

### WordPress, PHP and environment gotchas

- **The scratchpad directory is shared by parallel agents.** Another agent overwrote a cookie jar mid-test. Keep test files in a private subdirectory (`scratchpad/p2core/`, `scratchpad/p2v/`).
- **`wp_parse_auth_cookie()` and `wp_validate_auth_cookie()` read the request's own auth cookie when passed an empty string.** Never pass `''` from an empty stack; `BLT_Toolkit_Switch::newest()` returns `''` and callers test it first.

- **`WP_Locale_Switcher` caches the available languages when it boots.** To test SW-11 without language packs, pre-initialize the `get_available_languages` filter through WP-CLI `--exec` (or a router) so it exists before the switcher is built.
- **`wp_login_url()` is filtered by BLT Secure's custom slug; the slug path loads `index.php`, and `init` runs before BLT Secure serves `wp-login.php` on `wp_loaded`, so the switch handler on `init` works there.** `login_header()` exists at `init` only on a real `wp-login.php` request, so the interim-login result page needs that function check.

- **The switch-back link on `wp_die()` pages works without JavaScript by wrapping the `wp_die_handler` at `PHP_INT_MAX` and setting `link_url` and `link_text`.** Only HTML `wp_die()` uses that filter; AJAX, JSON and XML have their own.
- **Time A/B pairs, not separate rounds.** A router that pre-initializes an `option_active_plugins` filter dropping the plugin on alternate requests cancels drift; plain medians drifted 6% between identical rounds.
- **The command palette appends to a stale input on Enter.** Reopen it with an empty search in tests.
- **WooCommerce 11: User Switching's `forget_woocommerce_session()` alone is not enough.** `WC()->customer` is loaded at `init` 0 for the actor and saved into `WC()->session` on `shutdown`; after `forget_session()` the session key is already the new user's ID, so the actor's customer data overwrote the target's stored row. Re-read the new user's session with `init_session_cookie()` after unsetting the cookie from `$_COOKIE`, and swap `WC()->customer` through `initialize_cart()`.
- **WooCommerce 11 treats a session cookie that names another registered user as invalid and calls `destroy_session()`**, which deletes that user's stored row. A switch without forgetting therefore destroys the actor's session; the cart survives only through the persistent cart in user meta.
- **WooCommerce cart checks over HTTP:** the Store API `GET /?rest_route=/wc/store/v1/cart` needs an `X-WP-Nonce` from `admin-ajax.php?action=rest-nonce`, otherwise it answers for a guest; `GET /?add-to-cart=ID` adds a product; toolbar nodes print their attributes in single quotes.
- **`wp wc hpos sync`, then `wp wc hpos enable` or `disable`, switches order storage on SQLite in seconds.**
- **`GET /wp/v2/users?context=edit` lists only users the viewer may `edit_user`** (core skips the rest), so a Support Agent sees only itself; read the SW-27 field with the default `view` context.
- **The switch handler checks the capability before the nonce**, so a request with a junk nonce tells the two refusals apart: "Could not switch users." means the target is out of reach, "The link you followed has expired." means it is reachable. Handy for checking who may be switched into without minting nonces.

## 2026-10-22: Phase 2 review fixes

### Decisions

- **Two strengths of "who switched", as User Switching has: `old_user()` for display and the log, `original_user()` for switching back.** SW-3 scopes the stack to `SITECOOKIEPATH`, so with WordPress in its own directory (Bedrock, siteurl `/wp`) the front end and REST never receive it, and requiring it everywhere hid the toolbar node, the footer link (even after Switch Off), WooCommerce's links, `current_user_switched()` and the LOG-2 chain there. `old_user()` validates the old-user cookie (path `COOKIEPATH`), like User Switching's `get_old_user()`; only `request_switch_back()` also requires the newest stack entry (User Switching's `authenticate_old_user()`). WooCommerce and the compat shim call `old_user()`.
- **Stricter than User Switching: while someone is signed in, the old-user cookie counts only for the session its switch created** (`is_bound()`: the current session's `blt_switched_from_id` and `blt_switched_from_session` must match the cookie's user and the verifier of its token). Switch cookies left by someone else (a sign-in that fires no `wp_login`, such as an SSO plugin, or one made while the module was off) never offer a way into another account. A browser-sent cookie that fails validation or binding is expired at once (SEC-9: it no longer costs queries on every page for 48 hours); cookies written in the same request are never touched.
- **LOG-2's chain is rebuilt on the server from the session links, not from the stack cookie.** SPEC says the actor is "the first user in the switch stack"; the links (`blt_switched_from_id` plus the verifier) mirror the stack one for one, but are available on every request and cannot be edited by the browser. `follow_links()` is pure, with the session lookup injected; deeper than `MAX_DEPTH`, a loop, a missing verifier or a session that ended breaks the chain.
- **A switched session ends with the session it came from** (`end_orphaned_session()` on `determine_current_user`, priority 99). When any link back to the person who signed in is gone (sign-out elsewhere, "Log out everywhere", password reset, expiry, user deleted), the switched session is destroyed and the request is signed out. Signed out with an old-user cookie whose session is orphaned, `old_user()` ends what is left of the switch (`end_sessions()`). *Gap:* these endings are not logged, because a log write on `determine_current_user` would ask for the current user while WordPress is still deciding it (infinite recursion). Phase 7 could log them on `init` from a flag.
- **The target's session is capped at 48 hours** (`auth_cookie_expiration` filtered at `PHP_INT_MAX` around `wp_set_auth_cookie()` in `switch_to()`), so it never outlives the switch cookies. Since its length then no longer shows "Remember Me", the choice is stored in the new session key `blt_switched_remember` (an addition to SPEC 14.4), which `remember()` reads for nested switches and Switch Off.
- **Deviation from SW-3 (record per CLAUDE.md): the stack cookie path is `SITECOOKIEPATH` unless the login URL is outside it**, then the longest directory both share (`path_for()`, `stack_path()`). BLT Secure's slug is a home URL, so on a subdirectory install switching back through it always failed (403). Clearing sends deletions on both paths. User Switching has the same gap.
- **Deviation from User Switching 1.12.2 (SW-7): the switch cookies are browser-session cookies unless the person's own sign-in used "Remember Me".** User Switching always gives them 48 hours, so after a browser restart the login screen still signed the person back in without a password although they chose a non-persistent sign-in. The 48-hour limit stays inside each cookie value either way. The privacy text now says so.
- **Deviation from User Switching (SW-10): a sign-in or sign-out destroys every session the switch cookies could return to** (`BLT_Toolkit_Switch_Cookies::end_sessions()`, each entry validated with its own scheme first). Clearing only the cookies left the originating session, often an administrator's, live for up to 14 days, so any copy of a stack entry or of the original sign-in cookie still signed in after an explicit Log Out.
- **SW-10 holds with the Switch module off.** SPEC 4.1 says a disabled module registers no hooks but that protection holds with every module off; `BLT_Toolkit_Plugin::boot()` therefore adds `end_switch()` on `wp_login`, `wp_logout` and `blt_m365_sso_user_authenticated` when the switch module did not boot. It scans the cookie names first and loads the cookie class only when a switch cookie is present. Without it, cookies left while the module was off let whoever signed in next on that browser switch back into the original account once the module returned.
- **Switch Off is refused on a full stack**, like switch to (`is_full()`), so the oldest entry, the person who signed in, is never dropped; `push()` keeps its cap as a backstop.
- **The original user's row, profile button, REST search result and REST field give the switch-back URL** (User Switching's `maybe_switch_url()`), so nobody nests a switch into the account they came from. The labels still say "Switch To", as User Switching's do.
- **The "Viewing as" toolbar node links to the viewed user's profile** (or, for a user who cannot `read`, is a focusable item without a link, as core's account menu does), not to the switch-back action, whose accessible name it did not carry (WCAG 2.4.4). Switching back is its child node.
- **A signed-out page that shows the footer link is sent uncacheable** (`nocache_headers()` and `DONOTCACHEPAGE` on `template_redirect`). `template_redirect` rather than `send_headers`: `is_admin_bar_showing()` caches its answer in a global, and before the query runs it would cache a wrong one for embeds.

### WordPress, PHP and environment gotchas

- **`WP_Session_Tokens::get_session()` is protected and `get_all()` drops the verifier keys**, so a session cannot be looked up by verifier through the public API. `session_by_verifier()` binds a closure to the manager (`Closure::bind( fn, $manager, get_class( $manager ) )`), which also respects a custom `session_token_manager` and skips expired sessions; reading `session_tokens` meta directly would not.
- **Core never updates `$_COOKIE` when it sets the auth cookies, and SW-10 unsets the logged-in cookie on `clear_auth_cookie`**, so after `wp_set_auth_cookie()` in the same request `wp_get_session_token()` is empty. The switch flows keep the new session as `array( user ID, token )` for `current_session()`, so `current_user_switched()` inside a `switch_to_user` listener still answers.
- **Nothing on `determine_current_user` may call `wp_get_current_user()`, `is_user_logged_in()` or anything that logs**: it recurses. Use `get_userdata()` and `wp_parse_auth_cookie()` only.
- **A grid item's `min-width: auto` lets a 25em `regular-text` input widen its track past a 420px card** (grid blowout), so `max-width: 100%` alone did nothing. `.blt-toolkit .blt-field > * { min-width: 0 }` in the page CSS lets the cell shrink.
- **The duplicate-switch "Yes" link is relative (`/wp-login.php?…&force=1`); prefix the origin when following it with curl.**
- **To test WordPress in its own directory, a `php -S` router can set `WP_HOME` and `WP_SITEURL` (`/wp`), strip `/wp` from the path and set `SCRIPT_NAME` with the prefix**; static files under `/wp/` must then be served by the router with their content type. `COOKIEHASH` changes with the siteurl, so jars from the root setup do not carry over.
- **The Claude Code safety check refuses `rm` on a relative glob after a `cd` in the same command**; clear scratch files with `find /absolute/path -type f -delete`.

## 2026-10-22: Phase 3 (rename procedure, profile, author redirects, self-service)

### Decisions

- **A self rename keeps the current session and, with "Sign the person out everywhere" on, ends the user's other sessions.** UN-14 names `destroy_all()` only for other users; the other sessions of someone renaming themselves carry the old login in their cookies and are dead anyway, so they are ended as the setting says (`destroy_others()`), and the settings text ("Someone who changes their own username stays signed in") still holds. The re-issued cookie keeps the expiration of the cookie it replaces and its "Remember Me" (the switched session's `blt_switched_remember` when there is one), rather than a fresh 2 or 14 days as core's `wp_update_user()` gives after a password change.
- **The cookie is re-issued only when the request's logged-in cookie names this user under the old login and its token is a live session of theirs** (`BLT_Toolkit_Username_Changer::session_token()`). A job tick runs as the job's owner (JOB-3) from WP-Cron (no cookie) or from another administrator's browser (their token): re-issuing there would set a cookie with the wrong token, or create a session nobody holds. In those cases the owner's own browser is signed out, which the bulk dry run's "this is you" warning covers.
- **UN-12 leaves out the session a self rename keeps.** Someone switched into a user who renames themselves (X-4) keeps that switched session and can still switch back (verified), so warning about it would be wrong; their other switched sessions still count.
- **UN-22 in the profile path is checked on `user_profile_update_errors`, against the hash as stored before core saves the form**, because a new password in the same submit is saved before `profile_update`, where the old password would no longer match. `change()` checks the `current_password` option whenever it is passed, and requires it for the self-service sources (`self`, `shortcode`) when the setting is on, so a caller that forgets it fails closed. Bulk and REST never ask (an administrator's CSV is not self-service).
- **UN-6's message is generic for people who cannot `list_users`** (`BLT_Toolkit_Username_Changer::public_error_message()`): "That username is not available" instead of "the email address of another account", in the profile errors, the REST check and the bulk dry run, so self-service cannot confirm which addresses have accounts. The rule itself is unchanged. Core's registration and lost-password screens leak the same fact; this only avoids adding a faster oracle.
- **Previous author slugs are one `blt_toolkit_previous_nicenames` meta row per slug, not one serialized array**, so the 404 lookup is an exact `meta_value` match ordered by `umeta_id` (the newest rename wins when two users once had the slug). Each user keeps 20. The redirect runs only for a 404 that asked for `author_name`; an old slug's feed (`/author/old/feed/`) is not redirected, because core answers it with an empty feed and 200, not a 404.
- **`blt_toolkit_username_changed_at` is written only for self renames** (UN-21 is the self-service cooldown); a rename made by someone else does not restart it.
- **The profile result notice travels in a transient of the actor plus a `blt_tk_username=1` flag added to core's redirect** (`wp_redirect`, added for one use), so `admin_notices` reads nothing on any request without the flag. The flag is in `removable_query_args`.
- **The profile section uses core's `form-table` markup**, because it sits inside core's profile screen and must look like its neighbors; the "no `form-table`" rule is for BLT screens. Without JavaScript it is its own "Change username" section at the end of the form; with JavaScript its contents move into core's Username row.
- **Settings > Usernames self-service toggles (UN-20) do not fire `blt_toolkit_before_roles_save` / `after_roles_save`**, like `grant_admin()` and the Support Agent role: those hooks belong to the Phase 4 role store, whose `$context` values are still proposed. Phase 4 should route this write through the store with context `self_service`. Until then it follows the store's rules by hand: changes are the toggles the person changed against the drawn state (RO-1), each checked with `check_role_change()` (RO-4), a `before_save` snapshot or nothing (SNAP-1), one `update_option()` (RO-3), and a `usernames` / `roles_saved` log row with the diff and snapshot ID. A role the person may not change is drawn disabled with the Guard's reason and left out of the "shown" list, so it is never written.

### WordPress, browser and environment gotchas

- **SQLite Database Integration flushes the whole object cache on every `wp_redirect()`** (`activate.php` adds a `x_redirect_by` filter at `PHP_INT_MAX` that calls `wp_cache_flush()`, loaded by the `db.php` drop-in even though the plugin is inactive), and the dev sites' Redis drop-in sets no `WP_REDIS_SELECTIVE_FLUSH`, so that is a `FLUSHDB` of the shared Redis: every redirect by any agent's site wipes every site's cache. A stale-cache test (UC-1) then passes whether or not the code clears the cache, and transients vanish. For a meaningful test, serve through a router that pre-initializes `$GLOBALS['wp_filter']['init'][1]` with a callback that runs `remove_all_filters( 'x_redirect_by', PHP_INT_MAX )`, check the key in Redis (`redis-cli exists NAME.sqlitewp:userlogins:LOGIN`) right before and after, and run a negative control (a bare `$wpdb->update()` of `user_login` without `clean_user_cache()` still lets the old login sign in).
- **Never switch a dev site between Redis on and off without clearing its keys** (`redis-cli --scan --pattern 'NAME.sqlite*' | xargs -r redis-cli del`). Writes made with the cache off leave Redis stale, and core's profile save merges `get_userdata()` into `wp_update_user()`, so it wrote a stale `user_nicename` back to the database.
- **A `php -S` router must map a directory to its `index.php`** (`/wp-admin/` to `/wp-admin/index.php`); falling through to the site's `index.php` sends the front page, and a browser login then loops on redirects. Without a router, `php -S` does this itself.
- **Chrome moves focus back to the document when it scrolls to the URL fragment after `load`**, so a field focused on `DOMContentLoaded` for `#blt-tk-username` lost focus; focus it after `load` (and `scrollIntoView` there).
- **Core's narrow-screen profile CSS gives `.form-table td .description` its own `display`, which beats the `hidden` attribute**, so core's "Usernames cannot be changed." stayed visible at 420 px; set `style.display` as well.
- **WordPress 7.1 prints profile errors as `<div class="notice error"><p>…</p></div>` without an "Error:" prefix**; test parsers that look for `<div class="error">` find nothing.

## 2026-10-22: Phase 3 (bulk rename from CSV, UN-30)

### Decisions

- **LOG-2 for background jobs: `BLT_Toolkit_Jobs::start()` stores the starting request's switch chain in the job's `chain` key, and each tick runs inside `BLT_Toolkit_Log::with_switch_chain()`.** A tick runs as the job's owner (JOB-3) but in a request that carries nobody's cookies (WP-Cron, the loopback) or someone else's (REST ticks from another admin's tab), so the Switch module's provider cannot know who signed in. Without the pin, rows written by a loopback or WP-Cron tick of a bulk rename started while switched would name the switched-into user as the actor with no "acting as", since the provider sees no switch cookies there; with it they read actor 1 acting as 68 (verified, `tasks/todo.md`). An empty pinned chain means "not switched", so a tab that is switched now cannot rewrite a job started unswitched. A Retry failed pass keeps the chain of the original start, as it keeps the original owner.
- **The backup acknowledgment (CONVENTIONS 11, UN-30 step 5) lives in the sign-in session's data, key `blt_toolkit_backup_ack`** (`WP_Session_Tokens::update()`), an addition to SPEC 14.4. "The first time in a session" then means the WordPress session: a new sign-in, or a switch (its own session), asks again; signing out drops it. The control is a `.blt-toggle`, not a bare checkbox (DESIGN 2 wins on admin UI).
- **The dry run is kept for an hour in the transient `blt_toolkit_bulk_plan_{user ID}`, one per person, named by a random token that the URL and the confirm form carry**, so what starts is exactly the dry run that was shown and a stale tab cannot start a newer upload. It is stored gzcompressed and base64-encoded when zlib exists: a 5,000-row plan is about 1.3 MB serialized, over Memcached's default 1 MB item, and shrinks about tenfold (2,000 rows: 507 KB to 46 KB). Uninstall must remove `_transient_blt_toolkit_bulk_plan_%` (requested; `uninstall.php` is not this task's file).
- **A row whose user's current login is no longer the dry run's old login fails ("The username is now …") instead of renaming**, and a user who already has the new login counts as done. The first keeps a bulk rename from applying to a state nobody reviewed; the second makes `process()` safe to repeat after an interrupted tick, as the job runner requires.
- **UN-12 in bulk: starting the job confirms the switched-session warning for the rows the dry run flagged, and only those.** A row whose user became switched after the dry run fails with the changer's UN-12 message and can be retried when the session ends.
- **Renaming yourself in a bulk run signs you out.** The renames run in background ticks without your cookie, so the changer cannot re-issue it (UN-14 keeps the session only for a rename made in your own request); the dry run says so in a callout and the job reports a warning on that row. Running the self row in the foreground was rejected: it can sit in the middle of a chain.
- **The template lists every user the person may see: administrators are left out when SEC-6 hides them from that person, and someone without `list_users` gets only the users they may rename.** The dry run likewise treats hidden administrators as unknown users, so neither file nor screen shows their logins.
- **Recent changes shows every `usernames` log row to holders of `blt_view_toolkit_log`, and to everyone else only the rows they made** (actor = them). The screen's own capability is `blt_change_usernames`, and the log is a separate permission.
- **One bulk rename at a time:** starting while another `username_bulk` job is live is refused (`bulk_busy`). Two concurrent batches could interleave chains that were each planned against a state the other changes.
- **The start row (`bulk_rename`) is written from `blt_toolkit_before_job`**, which fires once the job is stored and before its first tick is queued. Written after `start()` returned, it landed after the first rename rows whenever the loopback tick ran in another PHP process (seen with three `php -S` workers).
- **Rows the job refuses before writing are logged by the bulk class (`username_changed`, status `failure`, details `batch` and the error code); a failed write is logged by the changer itself**, so every row of a run has exactly one entry per attempt.
- **The "author URL will change" warning predicts the slug without the uniqueness suffix** (`BLT_Toolkit_Username_Bulk::nicename_would_change()`, the changer's policy and base slug). `BLT_Toolkit_Username_Changer::new_nicename()` is private; making it public would let the warning reuse it exactly.

### WordPress, browser and environment gotchas

- **The single-threaded `php -S` serves a job's queued loopback ticks before the browser's next page**, so a screen opened right after starting a short job already shows it finished. Start the server with `PHP_CLI_SERVER_WORKERS=3` to watch a panel update live; SQLite coped with three workers.
- **In Playwright, `page.check( '#id', { force: true } )` on a `.blt-toggle` input sometimes reports "Clicking the checkbox did not change its state"**, because the input is visually hidden inside its label. Click the toggle's `.blt-toggle-label`, or focus the input and press Space, as a person would.
- **With `javaScriptEnabled: false`, `page.addStyleTag()` never resolves** (it waits for the style's load event), and full-page screenshots taken right after a form navigation can show the previous page ghosted over the new one. Open the URL in a fresh page with a tall viewport and take a plain screenshot instead.
- **`pkill -f "p3/card2.js"` killed the calling shell (exit 144)**, the same trap as the server pattern above: match the process with `ps -eo pid,args | awk` on exact fields.
- **WP-CLI's `user list --search` takes a wildcard only at the start or the end** (`*-new` works, `perf*-x` silently finds nothing); count with `$wpdb` and `LIKE` instead.

### WordPress, browser and environment gotchas

- **A row feeding into a cycle always claims a name the cycle also claims**, so the planner detects cycles before duplicate targets; the other order reports "More than one row renames a user to …" and hides D8's "Swap detected".
- **Per-row reason strings that listed every line of a group cost 180 MB on a 5,000-row cycle.** Build each group's reason once (PHP shares the string between rows) and cap the list at 20 lines (`BLT_Toolkit_Rename_Planner::MAX_LINES`).
- **Core's suffix truncation can cut inside a percent escape** (`…%d0%-2` for a long non-Latin login); `BLT_Toolkit_Nicename` mirrors it exactly, as the recorded vectors show.
- **`sanitize_user( $login, true )` strips non-ASCII, so non-Latin logins exist only on sites where a plugin filters `sanitize_user`.** The vector generator simulates that with a filter; long non-Latin logins then make core refuse with `user_nicename_too_long`, which `fits()` reports.
- **Counting delimiters only guesses the CSV delimiter**; `BLT_Toolkit_Csv` also accepts whichever delimiter makes a valid header.
- **WordPress 6.3 prints profile errors without escaping them**, so anything added to core's `WP_Error` on `user_profile_update_errors` must be escaped first (validator messages can contain what was typed). This supplements the 7.1 note in the Phase 3 entry above.
- **Block themes run `wptexturize()` over the whole rendered template after shortcodes run**, so shortcode text is texturized: a spaced hyphen becomes an en dash, a double hyphen an em dash, `1x2` a times sign. Print usernames and symbol lists inside `<code>`, which texturize skips.

- **A self rename with "Sign the person out everywhere" on ends the user's other sessions**, so a parallel cookie jar or Playwright login for the same user is signed out; log in again between scenarios.
- **Playwright: `waitForLoadState()` right after pressing Enter returns before the navigation starts**; use `Promise.all` with `waitForNavigation()`.
- **The job loopback posts its action in the body** (`admin-ajax.php`, `action=blt_toolkit_job_run`), so a router that blocks it must read `$_POST['action']`, not the URL.
- **A visitor's page view can spawn `wp-cron.php`, and that cron request reads `blt_toolkit_secrets` and `blt_family_opt_in`** (the update checker's token, `init` 1). Count front-end queries per request, or the cron request looks like a page view that queries.

- **"Hide the toolbar on the site" sits in Simple view's Basics card** (Appendix A) and is saved with the Simple form through `BLT_Toolkit_Settings::set()` with a `role_details_saved` log row (context `simple`). In Simple view the Role details card therefore leaves the toggle out and posts `keep_toolbar=1`, which `handle_details()` reads as "leave the flag as it is"; Advanced view keeps the toggle in that card.
- **"Edit in Advanced" opens Advanced narrowed to one Simple control** with the new `ctl` query argument (in `STATE_ARGS`; `visible_sections()` takes `only`). The quick filter matches one substring, so it could not show exactly a control's capabilities (themes' three, not all six `*_themes`). The toolbar's Apply and the group tree drop `ctl`.
- **Locks for a delegated role manager (SEC-3) are drawn, and the Guard decides.** A toggle that is not fully on and needs a capability the person lacks is disabled with a reason; a level whose default set needs one is a disabled option; Can delete is locked only when even Contribute's deletion is out of reach. The Guard's refusal (shown in the notice, capabilities named) is what actually stops a forged post.
- **The RS-7 "needs Can sign in to the dashboard" hint is one hint on the Basics control**, active while `read` is off and any dashboard permission is on, rather than one per control. RS-17's wording is used verbatim for the Media upload hint. Without JavaScript each hint is a link to the control it needs; "Also allow" is a script button.
- **Read-only content rows (RS-11, RS-12, RS-33) list their tier from the strings they use**, so an ACF-style type on `manage_options` reads Critical, and the "Controlled by" badge names the Simple control that owns the string.
- **The Roles screen dispatches the separate-permissions pages** (`?action=isolate|revert|cleanup&type=X`) to `BLT_Toolkit_Admin_Isolation::render()` before the role editor, as it does the lifecycle pages; the content row's buttons use `BLT_Toolkit_Admin_Isolation::url()`.
- **Owner question:** SPEC 10.6 names only multi-capability toggles as indeterminate. A single-capability toggle the role holds as `false` (a deny) reads Off; switching it on flips the deny, as in Advanced.

### WordPress, browser and environment gotchas

- **`.blt-ui .blt-callout` (and WordPress's `.button`) set `display`, which beats the `hidden` attribute**, so a callout or button the script hides stays visible. Add `[hidden] { display: none }` rules scoped to the container (`.blt-toolkit-dialog [hidden]`, `.blt-toolkit-simple-hint .button[hidden]`).
- **A test post type registered with `map_meta_cap => true` and a meta capability overridden to a primitive (`delete_post => manage_options`) makes core map every `current_user_can( 'manage_options' )` to `delete_post`** and log "map_meta_cap was called incorrectly" on every request. ACF-style fixtures need `map_meta_cap => false`, as WordPress itself leaves such types.
- **Playwright cannot click the label of a `.blt-toggle` whose checkbox is stretched over it** (the WCAG 2.4.11 fix): "input intercepts pointer events". Focus the checkbox and press Space, as a keyboard user would.
- **Read-only forms have no save bar, so no `blt_end` field**: a forged POST built from such a page must add `blt_end=1`, or the handler answers with the `max_input_vars` message before the Guard runs.

## 2026-10-22: Phase 5 (separate permissions and read-only enforcement)

### Decisions

- **RS-35: `bricks_template` is excluded from separate permissions by default, by reasoning, not by test (Bricks is not installed in the dev environment).** Bricks is a theme; it registers `bricks_template` with Posts' capabilities and decides who may build and manage templates through its own builder access setting per role plus `edit_posts` checks, and the builder saves templates over AJAX without asking for the type's `create_posts`. Isolated, the type's capabilities would not control template editing, so Simple view would show a level selector that does not do what it says. Owner can remove it through `blt_toolkit_isolation_excluded_types`; the Bricks smoke test (SPEC 18) is still owed.
- **Seeding copies denies and removes stale strings, so effective access is exactly unchanged.** Each new string takes the value of the Posts (or Pages) string it maps from, `false` included (a deny of `edit_posts` becomes a deny of `edit_{plural}` and `create_{plural}`); a new string a role or user already holds while holding none of its old strings (left from an earlier isolation, or by another plugin) is removed and the dry run says so. Users with Posts or Pages capabilities of their own are seeded through `BLT_Toolkit_User_Caps::save()` (context `isolation`, one `user_caps_changed` row each), every user change dry-run first so nothing is written when one would be refused. The confirm carries a SHA-256 of the whole plan (the RO-2 rule for isolation): roles or users that changed since the preview refuse the confirm.
- **Isolation and read-only enforcement register in `BLT_Toolkit_Plugin::boot()` next to the Guard, whatever the Roles module's state.** The filter that isolates types is added by the main file and applies regardless of modules, so its verification, notice and Plugins-row warning must load with it, and a View marker granted while the module ran keeps its meaning (SPEC 4.1: protection holds with every module off). Each only adds hooks.
- **The filter leaves a type alone when its registration no longer uses `post` or `page`** (its plugin gave it capabilities of its own since); RS-33 then reports it. It replaces `capabilities` entirely, as RS-31 states, so a plugin's explicit Posts strings cannot defeat isolation.
- **New option `blt_toolkit_isolation_state` (autoload yes):** `failed` (the RS-33 flag for Site Health), `reverted` (singular and plural of reverted types, which RS-32's cleanup needs after the settings entry is gone) and `shares` (Posts or Pages, for the revert page). It is written only on admin, cron and WP-CLI requests and only when something changed, and never read on a page view. A request that does not register an isolated type does not count it as failed, so a WP-CLI command without the fixture clears that type's flag. `uninstall.php` must delete it (requested; not this task's file). SPEC 14.2 does not list it.
- **RS-32's cleanup removes only strings the capability catalog flags as orphans (RO-11)** and logs `capability_deleted` (the existing Activity label), snapshot reason `before_isolation`. "Keep them" leaves the capabilities and forgets the step; they stay listed under Orphaned, where RO-24 can delete each. Revert writes no role and takes no snapshot.
- **Flow results reuse the role lifecycle's one-time notice** (`BLT_Toolkit_Admin_Role_Lifecycle::NOTICE_TRANSIENT` and `NOTICE_ARG`), so the role editor prints them after a redirect without a new mechanism.
- **Singular and plural are lowercased and must be 1 to 60 characters of `[a-z0-9_-]` with a letter, and differ**, so `edit_{singular}` never equals `edit_{plural}`; within the new set, a per-item name equal to a primitive (`published_events` with `events`) is a collision too.
- **The View level keeps core's front-end "View" row action** on published items; Edit, Quick Edit, Trash, bulk checkboxes and title links go, as RS-14 describes.

### WordPress, PHP and environment gotchas

- **Core refuses `edit.php?post_type=X` to someone holding `edit_X` but neither `edit_posts` nor `create_X`** ("Sorry, you are not allowed to access this page.", 403), which is exactly the View level on a type with its own capabilities. `wp-admin/includes/menu.php` drops the "Add New" item (no `create_posts`), then drops the submenu left with one item equal to its parent, so `get_admin_page_parent()` finds no parent and `user_can_access_admin_page()` falls back to `$_wp_menu_nopriv['edit.php']` (Posts). `BLT_Toolkit_Readonly::list_access()` registers the list once more on `admin_menu` (late) under a parent slug that is never drawn (`blt-toolkit-readonly`), with the type's `edit_posts` as its capability, only for users held read-only; nothing shows and nobody gains a capability.
- **`register_post_type()` turns `map_meta_cap` on by itself only when `capabilities` is empty** and the capability type is `post` or `page`; RS-31 sets `capabilities`, so it must also set `map_meta_cap => true` or every per-item check breaks. WordPress stores an array `capability_type` as its first element.
- **`get_post_type_capabilities()` records the per-item names in the global `$post_type_meta_caps`**, so a dry run must not call it for a type that is not isolated; `BLT_Toolkit_Isolation::caps_from_args()` rebuilds the same cap object without side effects (known vectors captured from 7.1 in `tests/test-isolation.php`).
- **In a shell, `S=… && cd $S && VAR=… nohup php -S … &` backgrounds the whole `&&` chain, so `S` is unset for the following lines**, and `$S/login.sh` wrote `/login.sh` and `/admin.jar` in the container root (a dev-site cookie jar; removal there is blocked by the safety check, so they are left for a person to delete). Put the server start in its own script.

## 2026-10-22: Phase 5 integration and verification

### Decisions

- **RS-15 is silent on several combinations giving the same set; detect() returns the one that claims the most** (highest level, then Can delete on, then the most Manage toggles on), not Custom. Types whose capabilities share strings make this real: ACF field groups map `edit_posts`, `delete_posts` and `create_posts` to `manage_options`, so Can delete on and off are the same set at Contribute, Author and Edit all. Returning the claimer is honest (every ability it describes is granted) and keeps a resave a no-op. Consequence: SPEC 17's literal `detect( apply( state ) ) === state` cannot hold for the ACF-style fixture; `test_rs15_round_trip_acf_style_cpt` asserts the canonical state and that saving it changes nothing, and `test_rs15_every_combination_has_a_distinct_set` proves the other five fixtures round-trip exactly.
- **Whether a taxonomy's `assign_terms` is dedicated (SPEC 10.3) is decided by the registry, not guessed by the mapper.** `BLT_Toolkit_Simple_Controls::type_map()` sets `assign_dedicated` false when `assign_terms` is a core capability, one of the row's own strings, or (added in integration) any content type's capability string, so a taxonomy shared by Events and Books with `assign_terms => edit_events` never makes a Books level grant `edit_events`. The mapper's own fallback (dedicated taxonomy, `assign_terms` not one of its manage, edit or delete strings) applies only when a caller omits the flag.
- **Overlapping universes are refused rather than merged.** The mapper asked that `changes_for()` merge overlapping on-page and checked sets so one row's removal cannot undo another's add; the registry instead refuses a save in which two changed controls want one capability both ways (`blt_toolkit_simple_overlap`) and merges adds and removes when they agree. That meets the request (no silent undo) and is stricter.
- **Separate permissions and read-only enforcement keep applying when the Roles module is off** by setting, by `BLT_TOOLKIT_DISABLE_MODULES` or by a legacy-plugin conflict (confirming the Phase 5 isolation decision above). SPEC 4.2 adds the isolation filter at file load before modules are read, and switching enforcement off with the module would silently widen access: a View-level role would regain editing of its own items. Verified on `p5verify` for all three ways of turning the module off. The pages that change them (isolate, revert, cleanup) live on the Roles screen and say "Nothing was changed: the Roles module is off" until it is back on; the RS-33 notice and the RS-34 Plugins row still show.
- **The marker prefix `blt_readonly_` is spelled out in four classes** (`BLT_Toolkit_Capability_Catalog`, `BLT_Toolkit_Simple_Mapper`, `BLT_Toolkit_Readonly`, `BLT_Toolkit_Isolation`) so enforcement and the `register_post_type_args` filter never load the 2,000-line catalog on a request (SEC-9). `test_rs13_marker_name` asserts all four are equal.

### Gotchas

- **For one level and Can delete value, if any choice of Manage toggles matches the granted set, so does the choice of every toggle whose strings are all granted.** Detection therefore needs at most nine comparisons, however many taxonomies a row has.
- **A `map_meta_cap` false type has no `edit_published_posts`, `edit_private_posts`, `delete_published_posts`, `delete_private_posts` or `delete_others_posts` keys.** The mapper reads only the SPEC 10.4 keys and treats a missing one as adding nothing; the per-item names (`edit_ledger`) are never part of a row.
- **`read`, `exist` and `do_not_allow` are kept out of every content row's universe**, so a level change can never take dashboard access away (`read` belongs to the Basics control).
- **A `<dialog>` closed with Escape fires `cancel`, not the Cancel button's click.** The Simple view's "switch view" dialog cleared its pending `then_view` only on the button, so Escape followed by a normal save landed in the other view. Both dialogs now clear it on `cancel` (found in the keyboard-only pass).
- **`tests/` is excluded by `phpcs.xml.dist`**; run `vendor/bin/phpcbf --standard=WordPress-Extra` on a new test file to keep its alignment tidy anyway.
- **On a dev site with plain permalinks, `/wp-json/...` is not the REST API**: a `POST /wp-json/wp/v2/event` answers 200 with the home page and changes nothing, which reads like a permission failure that did not happen. Use `/?rest_route=/wp/v2/event`.
- **`curl --data-binary @file` sends the file's trailing newline**, so the last field of a body printed by a script arrives as `1\n` and a strict `'1' === $value` check reads it as off. Strip the newline (`tr -d '\n'`) or end bodies with a field whose value is not compared.

## 2026-10-22: SEC-9 performance pass

Site: the SPEC 18 MySQL copy (`/home/user/wp-dev/wp-mysql`, MariaDB 10.11, WordPress 7.1.3, PHP 8.3 with opcache, no object cache) with exactly 10,000 users: 8,499 subscribers, 1,000 authors, 400 editors, 99 contributors, 1 administrator and the user manager `mgr` (a subscriber converted to the role `usermgr`: `read`, `level_0`, `list_users`, `edit_users`, `promote_users`, `create_users`, `delete_users`, `remove_users`, `blt_switch_users`, `blt_change_usernames`). Method: paired, interleaved A/B through a scratch router (plugin dropped through `option_active_plugins` on alternate requests, order random within each pair), `php -S` pinned to one core and MariaDB to another, in-request wall time plus PHP CPU time (`getrusage`), medians of the per-pair ratio with a bootstrap 90% interval. A copy of the tree with only this pass's seven files reverted (Phase 5's lines in `Plugin::boot()` kept) served as "before" in the same runs.

### Findings

- **The manager's overrun was SEC-6's list query, not the Guard's per-row checks.** `role__not_in => administrator` becomes a `NOT LIKE '%"administrator"%'` join on the capabilities rows, and with the total core asks for (`SQL_CALC_FOUND_ROWS`) MariaDB reads every user's rows: 24 ms on a warm server (149 ms in the first, colder runs), against 1 ms for the same list without the clause and 0.7 ms for the same join without the total. It made the manager's Users screen +35% at 20 rows and +49% at 100.
- **Core's own `count_users()` is a third of the page**: about 35 ms of about 95 ms with 10,000 users, seven collation-aware `LIKE` columns over every capabilities row (`utf8mb4_unicode_520_ci`; `LIKE BINARY` would be about 25% faster). It runs in both arms, and its swing (31 to 40 ms) is most of the measurement noise: ±3% on page medians even with 100 pairs. PHP CPU time per request is far steadier and is what attributed costs here.
- **Per row, core spends about 270 µs of CPU on wp-admin** (`single_row()`); BLT Toolkit added about 145 µs per row before this pass and about 95 after.
- **Both row actions read `$user->display_name`**, and in wp-admin core runs `sanitize_text_field()`, `wp_kses_data()` and `_wp_specialchars()` over it on every read of a user object in the `display` context, which `single_row()` sets: 8 to 15 µs a read, twice a row. WP-CLI never showed it, because those filters are added only when `is_admin()`; define `WP_ADMIN` through `--exec` to benchmark admin-screen code.
- **The rename action built the edit link again** (`get_edit_user_link()`, 16 to 40 µs) after core had built the same one for the row, and asked `edit_user` a second time.
- **The Guard built a new `WP_User` for the target on every guarded check** (`get_userdata()` merges role capabilities each time) and hashed both users' capabilities (`md5( wp_json_encode() )`) on every SEC-2 comparison; a row asks about the same target eight or nine times.
- **`BLT_Family::get()` builds the family's translated group list before it checks the opt-in**, and the update token's two non-autoloaded options were read in two queries, on every admin request.
- **Isolated micro-benchmarks under-estimate in-page costs by two to three times** (cache pressure in a full request). Attribute inside real requests: wrap the callbacks of every hook whose code lives in the plugin with `hrtime()` timers, installed at `plugins_loaded`, `init`, `admin_init` and `load-users.php` at `PHP_INT_MAX` so late registrations are caught; xhprof (`php8.3-xhprof`, loaded only with `-d extension=xhprof`) is useful for proportions and call counts, not absolute times.
- **Loading the plugin's 28 class files costs 60 to 130 µs under opcache**; deferring class loading is not worth it.

### Decisions

- **SEC-6 leaves administrators out by ID** (`BLT_Toolkit_Guard::hide_admins_in()`): the list table and REST filters mark the query with the query variable `blt_toolkit_hide_admins` (the administrator IDs) and a `pre_user_query` callback adds `AND ID NOT IN (…)` to that query's WHERE clause, so the results and the total both leave them out. Not `exclude`, which core ignores whenever `include` is set (`GET /wp/v2/users?include=1`). Administrators are still "users whose capabilities row contains `"administrator"`", exactly what the `NOT LIKE` matched, so the same people are hidden.
- **On users.php the IDs come from the counting scan** (`census()`): one query with the columns of core's counting query, the administrator column replaced by `GROUP_CONCAT()` of their IDs, run by whichever of the list query and `pre_count_users` comes first, plus one query over the administrators' rows by ID for what to subtract from the other roles' counts. It costs what core's count costs (35.2 against 34.1 ms, interleaved). The view counts are identical to the previous replacement. A list that may have been cut by `group_concat_max_len` (within 32 bytes of the limit, which is 1,024 bytes by default on MySQL and unknown, so assumed 1,024, on the SQLite drop-in) or two queries that disagree fall back to the old count query plus `admin_ids()`. On the SQLite drop-in (checked on a private dev site) the census runs as one query: it returns NULL for the variable and never cuts the list. The pure parts (`concat_ids()`, `census_counts()`, `id_list()`) are unit-tested in `tests/test-guard.php`.
- **Elsewhere (REST, large sites where core does not count) `admin_ids()` reads the IDs with one query** and keeps them in the object cache group `blt_toolkit` under core's `users` last-changed time, which core moves on every user, user meta and role change (`added_user_meta`, `updated_user_meta`, `deleted_user_meta`, `set_user_role`, `add_user_role`, `remove_user_role`, `clean_user_cache`): as fresh as WP_User_Query's own cached results, persistent with an object cache (entries expire after a day, since each change makes a new key), per request without one (about 13 ms with 10,000 users). If the IDs cannot be read the query falls back to `role__not_in`: slower, never an administrator shown.
- **Accepted differences, all outside the SEC rules:** a user with no capabilities row at all is now listed for a user manager, as for an administrator (core's `NOT LIKE` clause dropped them as a side effect; Phase 4's No role view already listed them, and no SEC rule protects them); a user with two capabilities rows, one of them `administrator`, is now hidden where the join listed them through the other row; and rows that tie on the sort column can come back in another order (sorting the seeded site by email, where 9,999 emails are empty, gave the administrator's order minus the administrator instead of the old join's order).
- **Row actions:** `BLT_Toolkit_Plugin::display_name()` gives `$user->display_name` exactly, reading it once per viewer, user, context and stored value, and on users.php reuses the read core already made for its "View posts by" link (noted by a `user_display_name` filter at `PHP_INT_MIN` and `PHP_INT_MAX`); the rename action reuses the edit link core built for the row (noted at `PHP_INT_MAX` on `get_edit_user_link`) and, because core runs that filter only after `current_user_can( 'edit_user' )` passed, takes it as that answer while core's `users` last-changed time is unchanged and no role definition was written (otherwise it asks); switch links compute `wp_login_url()` once per request from `wp_loaded` on (each still gets its own nonce).
- **Guard:** the target `WP_User` is reused while core's `users` last-changed time is unchanged (`flush()` drops it with the rest when role definitions change), and a user's capability fingerprint is reused for an identical `$user->caps` array. Every rule is still evaluated, filters included, on every check.
- **Settings:** admin requests read BLT Toolkit's options that are not autoloaded in one query, at `init` priority 0 (`BLT_Toolkit_Settings::prime_admin_options()`, WordPress 6.4 and later): the token's secrets and the family opt-in (read by `github_token()` at `init` 1), the update checker's state `external_updates-blt-toolkit` (read by `menu.php`), and on users.php the No role view's transient pair (`prime_also()`, from `BLT_Toolkit_User_Roles::boot()`). The administrator's Users screen runs 34 queries against 33 with the plugin inactive (36 before), the manager's 28 against 26 (30 before). The shared token is looked up only when the owner opted BLT Toolkit in to the `github` group, which gives the same answer as `BLT_Family::get()` without building its group list.

### Left open

- **Fixed cost outside this pass's files** (about half of the 3.5 to 4.5 ms of extra CPU on every users.php load): the update checker (loading and setting up its library, then `injectUpdate` five times a request, about 1 ms), `BLT_Toolkit_Admin::register_menu()` (0.2 to 0.3 ms), `BLT_Toolkit_Log::register_job_type()` (0.1 ms), the Switch privacy text on `admin_init` (0.1 ms), and Phase 5's read-only `map_meta_cap` closure (0.1 ms at 20 rows, 0.3 ms at 100). The No role view looks expensive in a profile (0.7 ms) but costs 0.3 ms of CPU in an A/B with it removed: the rest is kses and translation setup that core otherwise does a little later for the rows.
- **Per row, the floor is the two meta-capability checks** (`blt_switch_to_user`, `blt_change_username`; they must go through `current_user_can()` per target so other plugins' filters apply), the per-target switch nonce (SEC-7) and escaping: about 85 µs of CPU per row in the page. So 100 rows per page stays above 10%.
- **Large sites without an object cache** pay `admin_ids()`'s scan (O(users), about 13 ms per 10,000) on every users.php load and REST collection request from someone administrators are hidden from, where core skips counting. Still about half the old join's cost; with an object cache it is one cache read.

### Gotchas

- **10,001 users is a large site**: `wp_is_large_user_count()` is `user_count > 10000`, so adding the test manager to a 10,000-user seed made core stop counting and changed what was measured. Convert an existing user instead, then run `wp_update_user_counts()`.
- **The old SEC-6 join took 149 ms on the first runs after seeding and 24 ms once the server had settled**, while core's own pages barely moved: a query that reads every capabilities row is at the mercy of the buffer pool and the plan. Warm the server and measure at the default page size as well as a stress size.
- **`pkill -f PATTERN` matches the shell running it when PATTERN is in its own command line**, which killed the tool's shell (exit 144). Stop processes by exact PID.
- **A "before" copy of the plugin for interleaved runs must start from the live tree**, not HEAD: the Phase 5 team had added two `register()` calls to `BLT_Toolkit_Plugin::boot()` in the same file, so a HEAD copy measured a different plugin.
