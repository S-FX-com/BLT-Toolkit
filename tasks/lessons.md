# Lessons

Gotchas found while building, and decisions recorded with their reasons (including every **Should** in `SPEC.md` that is not followed, and every SPEC and `DESIGN.md` conflict, per `CLAUDE.md`). Append only; never rewrite history. Newest at the bottom.

## 2026-10-21: Phase 0 decisions

- **The repository and the update checker point at different places; owner to confirm.** The repository currently lives at `github.com/sfxdotcom/BLT-Toolkit`, but SPEC 3 names `S-FX-com/BLT-Toolkit`. The update checker in `blt-toolkit.php` points at `https://github.com/S-FX-com/BLT-Toolkit/`, as SPEC 3 says, so releases must be published there (or the repository transferred there) before installed sites can find them. Until then the Phase 0 criterion "a second release updates a test site through the updater" cannot pass. CONVENTIONS 17, item 8 records the same `sfxdotcom` versus `S-FX-com` question for BLT Secure.
- **Vendored files come from BLT Activity Log, which matches BLT Secure; BLT Events has drifted.** `assets/css/blt-design-system.css` and plugin-update-checker (`includes/lib/plugin-update-checker/`, v5p7) were vendored from BLT Activity Log and match BLT Secure byte for byte (checked with `sha256sum` and `diff -r`; the stylesheet's SHA-256 starts `72ea81f0`), as do `DESIGN.md`, `CONVENTIONS.md`, `includes/blt-family/`, `blt-family-smoke.php` and `assets/img/`. BLT Events carries a drifted `blt-design-system.css` (Events-specific rules such as `.blt-badge-trash`, `.blt-review-reason` and the solid status badges) and an older update checker (v5p6). That is family drift to resolve in the canonical copy and port to every repo in one pass (CONVENTIONS 16.3, rule 3), not here.
- **Version 0.1.0 while phases are built; 1.0.0 comes from `#major`.** The header, `BLT_TOOLKIT_VERSION` and the `readme.txt` stable tag stay at 0.1.0 while the phases are built, and nobody bumps them by hand. CI bumps patch by default, so the first release after a merge publishes 0.1.1. Put `#major` in the message of the merge that completes Phase 7 to publish 1.0.0.
- **Uninstall removes only BLT Toolkit's own capabilities, not "every `blt_*` capability".** SPEC 14.6 says uninstall "removes every `blt_*` capability". Read literally, that would also strip other BLT plugins' capabilities from roles and users (`blt_view_activity_log` from BLT Activity Log, `blt_manage_documents` from BLT Documents) and break those plugins. `uninstall.php` therefore removes only the nine capabilities in SPEC 5.1 and the `blt_readonly_*` markers. This follows the intent of SPEC 14.6 and CONVENTIONS 11 ("never delete things the plugin does not own").
- **SPEC 21 decisions D1 to D14 are adopted as recommended unless the owner overrides them; D4 and D14 still need confirmation.** D4 (menu placement): a top-level BLT Toolkit menu whose submenus carry their own capabilities, plus Users > Roles. `DESIGN.md`'s admin menu example registers one entry under `manage_options` at position 58, CONVENTIONS 6.1 describes "one menu entry, one capability", and the family's menu position is still open (CONVENTIONS 17, item 16: Documents uses 81, the `DESIGN.md` snippet 58). D14 (front-end prefix): `.blt-tk-*` and `--blt-tk-*`, pending confirmation of BLT Tube's prefix. Both are listed under "Open decisions" in `tasks/todo.md`.

## 2026-10-21: Phase 0 build

### Core services

- **The update token is resolved on `init` (priority 1), not on `plugins_loaded`.** `BLT_Family::get()` runs `__()` through `BLT_Family_Groups`, and before `init` that calls `determine_locale()` / `get_user_locale()`, which authenticates the current user early, before SSO plugins add their `determine_current_user` filters. Every request path of the update checker (`admin_init`, cron events, WP-CLI) comes after `init`, so nothing is lost.
- **The update checker variable is not a PHP global under WP-CLI.** WP-CLI loads plugin files inside a function scope. Do not rely on `$GLOBALS['blt_toolkit_update_checker']` outside HTTP requests.
- **`grant_admin()` adds only capabilities the `administrator` role does not mention, and keeps an explicit `false` (deny).** Reactivating must not undo a deliberate owner edit; SEC-14 recovery is the way back from a damaged administrator role. SPEC 5.1 says "granted on activation" without covering explicit denials, so this is a recorded interpretation.
- **`grant_admin()` takes `Snapshots::take( 'before_save' )` before it writes (SNAP-1).** On first activation that snapshot is skipped as a duplicate of the baseline taken a moment earlier, so a fresh activation leaves exactly one row.
- **`blt_toolkit_lockout_critical_caps` can add capabilities but never shrink the SEC-12 base set, because that set is the anti-lockout guarantee.** `blt_toolkit_risky_caps`, by contrast, fully replaces the tier lists, since tiers are a classification. Tier entries may end in `*` as a prefix wildcard (`edit_others_*`), and Critical wins over Elevated.
- **BLT Secure's crypto rejects an AES-GCM envelope of exactly 28 bytes (empty plaintext) as tampered (`<= 28`).** Our copy uses `< 28`, with a unit test. Consider porting the fix to BLT Secure and the other `*_Crypto` copies.
- **`Settings::save_tab()` takes the tab's fields flat, keyed as in the group (General uses the module keys).** A missing toggle is false; a missing or invalid non-toggle keeps the stored value; integers are clamped (`min_length` 1 to 60, `cooldown_days` 0 to 365, `snapshot_retention` 1 to 500, `retention_days` 1 to 3650). These ranges are our choice; SPEC gives only defaults.
- **The disallowed-usernames list is stored lowercased**, through `sanitize_user()` (non-strict) and `strtolower()` as core does, because UN-4 compares case-insensitively on both sides.
- **`role_meta` entries that carry no information (empty description, toolbar shown) are dropped on write** to keep the autoloaded option small. Role IDs are sanitized to `[A-Za-z0-9_-]` with case preserved, so they still match existing roles.
- **`github_token_status()` reports `undecryptable` ahead of `shared`**, so the Advanced tab asks for the plugin's own token again even while a shared token is in use. A decrypt failure never deletes the envelope (a read never writes), so restoring the old salts brings the token back.
- **Deactivation and uninstall clear cron by scanning `_get_cron_array()` for hooks prefixed `blt_toolkit_`**, so hooks added in later phases are covered without updating a list. The update checker removes its own cron on deactivation; uninstall clears `puc_cron_check_updates-blt-toolkit` and `external_updates-blt-toolkit` explicitly.
- **`BLT_Toolkit_Plugin::is_active()` means "booted on this request"**, so it is false on multisite, before `plugins_loaded` priority 1, and in the activation request. Use `module_status()` for the configured state.
- **Settings writes start from the request-start copy of the option.** Two admins saving different tabs at the same moment could overwrite each other's group. Acceptable for Phase 0; RO-2-style locking may be wanted for `role_meta` and `isolated_post_types` in Phases 4 and 5.
- **`Snapshots::take()` returns 0 and calls `error_log()` on failure but does not block the write.** Phase 1 decides whether a failed SNAP-1 snapshot must stop a roles write.

### Tooling and CI

- **Composer run as root in a non-interactive session disables plugins**, so `dealerdirect/phpcodesniffer-composer-installer` never registers WPCS (`phpcs -i` lists only PEAR, PSR, Squiz and Zend) and `composer <script>` aborts. In the cloud dev container, run `COMPOSER_ALLOW_SUPERUSER=1 composer lint|phpcs|test`, and after a fresh install either run `vendor/bin/phpcs --config-set installed_paths` with the absolute paths of `vendor/phpcompatibility/*`, `vendor/phpcsstandards/*` and `vendor/wp-coding-standards/wpcs`, or install with `COMPOSER_ALLOW_SUPERUSER=1`. CI runs as a non-root user and is unaffected.
- **The family release pipeline (BLT Secure, BLT Activity Log) runs `git tag vX` (lightweight) then `git push --follow-tags`, which pushes only annotated tags** (confirmed in a throwaway repo), so the tag was really being created by `softprops/action-gh-release` through the API at the default branch head. BLT Toolkit's `release.yml` commits, rebases, creates an annotated tag, then runs `git push origin main refs/tags/vX`. It also builds and verifies the zip before pushing, so a tree that cannot be packaged never gets a version commit or tag, then rebuilds after the push so the asset matches the tagged commit.
- **`release.yml` keeps everything BLT Secure's does that BLT Activity Log dropped**: the explicit greps of the header, `BLT_TOOLKIT_VERSION` and the Stable tag at the new version. They run alongside `check-version-sync.sh`.
- **BLT Activity Log's `build-zip.sh` rsyncs `./` into `build/` without excluding `build/`**, which can ship an empty `build/` folder inside the zip. BLT Toolkit has `/build` in `.distignore`, passes `--exclude=/build` to rsync, and `verify-zip.sh` fails on a `build/` folder.
- **POT drift check: the CI release bump changes the header version without regenerating the POT, and the copyright year changes on January 1.** BLT Activity Log's check (which ignores only `POT-Creation-Date`) would fail the next PR. BLT Toolkit also ignores the `Project-Id-Version` and `# Copyright` lines, and fails when the POT is untracked, because `git diff --quiet` passes for untracked files.
- **`make-pot.js` deviates from BLT Activity Log's, each time to match `wp i18n make-pot`:** it sorts by path, then numeric line, comparing code units (Activity Log's `localeCompare` is locale-dependent, so CI and laptops could disagree and report false drift); it attaches translators comments placed earlier in the same statement, in block, docblock or `//` style (Activity Log missed the common `/* translators */` line followed by `printf( esc_html__( ... ) )`); it extracts `wp.i18n.*` calls in JS and skips comments inside argument lists; and it writes the plugin header strings, merged with a matching string in the code. Intended differences from WP-CLI: `$obj->__()` method calls and concatenated literals are not extracted (WPCS rejects concatenation anyway).
- **PrefixAllGlobals matches prefixes with `stripos( ... ) === 0`, so listing `current_user_switched` as a prefix whitelists that one function name without excluding its file.** Do not whitelist `switch_to_user`, `switch_back_user` or `switch_off_user` the same way: that would also allow declaring `switch_to_user()`, which GEN-2 forbids. The SW-19 compat `do_action()` calls need an inline `// phpcs:ignore WordPress.NamingConventions.PrefixAllGlobals.NonPrefixedHooknameFound -- SW-19 compat: User Switching's action name.` instead.
- **WordPress-Extra includes `Universal.Files.SeparateFunctionsFromOO`**, so the `current_user_switched()` shim (SW-19) must live in a functions-only file, inside a `function_exists()` guard, that the switch module requires explicitly, not inside a class file.
- **`bump-version.php` has no ABSPATH guard on purpose**: it is a CLI script that runs without WordPress and never ships (`.github` is excluded from the zip). The "every PHP file" rule is about plugin files. It keeps the `@package Blt_Toolkit` docblock. `tests/test-bump-version.php` is BLT Activity Log's test, renamed.
- **Every downloadable SQLite Database Integration release (2.1.13 and later) declares "Requires at least: 6.4".** The `db.php` drop-in loads it without activating it, and WordPress 6.3 installs and runs with 3.1.1 (verified). `BLT_SQLITE_VERSION` can pin another release.
- **The shared `blt-site stop PORT` uses `pkill -f "php -S localhost:PORT"`, a prefix match, so `stop 890` would also kill a server on 8903.** The helper generated by `bin/dev-site.sh` adds a trailing space to the pattern. Reusing a site NAME with Redis on would read the old database's cached objects, so the drop-in uses a per-install, per-database prefix with `WP_REDIS_SELECTIVE_FLUSH`, and `blt-site new` flushes that site's keys when `BLT_OBJECT_CACHE=redis`.
- **The dev container has no rsync, so `build-zip.sh` falls back to its own copy**, which supports root-anchored `/path` patterns and bare names or globs, and fails on any other `.distignore` pattern shape. CI keeps BLT Activity Log's rsync invocation. Only the fallback has been run locally.
- **Commit `.github/scripts/*.sh`, `bin/dev-site.sh` and `bin/make-pot.js` with mode 100755**, as BLT Activity Log does; `bump-version.php` and the workflows are 100644. Run `node bin/make-pot.js` right before committing so `languages/blt-toolkit.pot` matches the final strings.

### Admin screens

- **Menu position 81 (D4; CONVENTIONS 17, item 16).** BLT Secure registers its top level at 81 and the shared BLT family screen (`BLT_Family_Admin`) at 80; CONVENTIONS 17 says Documents uses 81 too. BLT Events has no top-level page of its own (its menu is its CPT, with `menu_position` null). 81 keeps the family's menus together just below Settings, and WordPress shifts a taken position by a fraction, so two plugins on 81 coexist.
- **Users > Roles (D4) is `add_users_page()` with the menu slug `admin.php?page=blt-toolkit-roles` and no callback.** WordPress prints the slug as a plain href and registers no second page, so `get_admin_page_parent()` still resolves to `blt-toolkit` and the BLT Toolkit menu is the one highlighted on the Roles screen. For a user without `edit_users`, `add_users_page()` files the link under Profile; that is expected.
- **Per-submenu capabilities under a `manage_options` top level work as SPEC 13.1 wants.** Verified with a user holding only `read` and `blt_edit_roles`: WordPress repoints the top-level link to the first submenu they can reach (Roles), and the page's hook suffix stays `blt-toolkit_page_blt-toolkit-roles`, so gating assets on the hook `add_submenu_page()` returned still works. Never hard-code hook suffixes: they derive from `sanitize_title()` of the translated menu title.
- **`wp_nonce_field()` gives the input an `id` equal to its name, so a screen with several forms repeats that id.** `BLT_Toolkit_Admin::form_fields()` prints the hidden action and nonce inputs by hand, with no id. `check_admin_referer()` needs only the nonce.
- **Settings > Advanced puts Test connection and Remove token inside the token card as `<button form="...">` pointing at two small standalone forms printed after the main form.** That gives separate POSTs, no nested forms and no JavaScript. Pressing Enter in the token field still submits the main form, because buttons that belong to other forms do not count as its default button.
- **Overview module cards use the selectable-card styling on a `<div>`, with a `.blt-toggle` inside as the control, rather than the catalog's label-plus-hidden-input form.** DESIGN 2 says to toggle `.is-selected` with JS, and the plugin ships no admin JS in Phase 0. Here `.is-selected` is server-rendered and means "this module is running now", while the toggle shows the saved setting. Nesting a toggle label inside a label card would be invalid HTML.
- **Should-level deviation from the catalog: `nicename_policy` (Usernames) and `default_view` (Roles) are `<select>`s, not radio selectable cards.** Without JS a selectable card's hidden radio gives no visible feedback until save. Revisit when the plugin ships an admin script.
- **PRG notices carry only a whitelisted code plus integer or `sanitize_key()` arguments (`http`, `via`, `err`), never message text.** Unknown codes render nothing. Notices print with the `inline` class so core's script does not move them above the page header.
- **`route_post()` checks the POST method (405), then the action's capability (403), then the nonce.** A delegated user posting to a settings action gets "You do not have permission to do that." even with a junk nonce, and nothing is written.
- **`github_token_status()` decrypts the stored token, so `Settings::render()` calls it only on the Advanced tab.** Test connection sends the token only as an `Authorization: Bearer` header; the redirect carries the HTTP status and the token's source (`constant|stored|shared|none`), never the token.
- **To render a screen in the `conflict` or `disabled` state without touching the shared WordPress core** (an mu-plugin there would leak into every agent's site), run `blt-site wp NAME --exec='class user_switching {} define("BLT_TOOLKIT_DISABLE_MODULES","usernames");' eval-file render.php`. `--exec` runs before plugins load, so GEN-1 detection and SEC-15 both see it.
- **In this sandbox, `wp_remote_get()` to api.github.com from the dev server receives HTTP 403 from the agent proxy.** Verify the Test connection branches with a `pre_http_request` mock, plus a `wp_redirect` filter that throws so the handler's `exit` is skipped. In PHP test harnesses, beware that a `'404'` array key becomes the integer 404.

### Verification

- **Never run `wp plugin uninstall blt-toolkit` on a dev site:** `wp-content/plugins/blt-toolkit` is a symlink to the repo and WP-CLI deletes the plugin directory. Test uninstall by deactivating, then `blt-site wp NAME eval 'define( "WP_UNINSTALL_PLUGIN", "blt-toolkit/blt-toolkit.php" ); include "/home/user/BLT-Toolkit/uninstall.php";'`. Deactivation already clears the `blt_toolkit_*` and update-checker cron events, so re-add some before uninstalling to prove uninstall clears them too.
- **To verify "no front-end queries", run `php -S` with a scratch router that defines `SAVEQUERIES` and dumps `$wpdb->queries` with caller chains on shutdown,** then compare against the same requests with the plugin inactive. The SQLite drop-in records callers, so BLT frames can be grepped directly, and no mu-plugin goes into the shared core.
- **A `php -S` router runs in WordPress's global scope, so its own variables must not be named `$wp`, `$path` or anything else WordPress uses as a global.** A router that set `$wp` broke every request with "Call to a member function add_query_var() on string".
- **`pkill -f "php -S localhost:PORT"` also matches the shell that runs it when the same command line contains that text, and kills it (exit 144).** Stop a server from a compound command with an exact match instead: `ps -eo pid,args | awk '$2=="php" && $3=="-S" && $4=="localhost:PORT" {print $1}' | xargs -r kill`.
- **`wp core multisite-convert` writes the multisite constants into `wp-config.php`, which every dev site shares.** Use `--skip-config`, then pass the constants per process: `--exec='define( "MULTISITE", true ); …'` for WP-CLI and a `php -S` router that defines them for HTTP. With that, SQLite Database Integration 3.1.1 runs a real network (network admin, per-site and network activation), so D1 was verified on SQLite.
- **Over HTTP, the multisite refusal answers 500 with the `wp_die()` page while carrying the `Location: plugins.php?error=true…` header that `activate_plugin()` set before running the hook.** Browsers and `curl -L` do not follow `Location` on a 5xx, so the person sees the readable message and its Back link; the plugin is not recorded as active.
- **WordPress 6.3 on PHP 8.3 logs core's "Calling get_class() without arguments is deprecated" (`class-wp-http.php` line 329) on every `WP_Http` request**, including at install and login before BLT Toolkit is active. It is not a BLT Toolkit notice, and SPEC pairs 6.3 with PHP 7.4, where it does not fire. Read a 6.3 debug log with that line in mind.

## 2026-10-21: Phase 0 review fixes

- **`enableReleaseAssets( $regex )` alone still installs source archives.** Its default, `Api::PREFER_RELEASE_ASSETS`, offers a release's `zipball_url` when no asset matches, and even `REQUIRE_RELEASE_ASSETS` alone only makes that release count as none, after which plugin-update-checker's GitHub strategies fall back to the newest tag's zipball and then the branch. A release can lack its asset for real: `softprops/action-gh-release` creates the release before it uploads, and anyone can make a release by hand. `blt-toolkit.php` passes `REQUIRE_RELEASE_ASSETS` and keeps only the `latest_release` strategy through `$checker->addFilter( 'vcs_update_detection_strategies', ... )` (the filter `puc_vcs_update_detection_strategies-blt-toolkit`). This deviates from the BLT Secure (`includes/class-updater.php`) and BLT Activity Log (`blt-activity-log.php`) copies, which share the gap; port both lines to them in one family pass (CONVENTIONS 16.3, rule 3). Consequence to know: a release whose upload failed offers no update until the zip is attached to it.
- **CI did not run on `main`, and `release.yml` had no quality gate, so a red tree could be bumped, tagged and shipped.** `ci.yml` had `branches-ignore: main` (copied from BLT Activity Log) and nothing makes a merge wait for pull request checks. `release.yml` now runs `composer lint`, `composer phpcs`, `composer test` and the POT drift check before "Bump version", and `ci.yml` runs on every push, `main` included. The release's POT check runs `git checkout` on the POT afterwards, because the bump step's `git commit -am` would otherwise commit the regenerated creation date. BLT Activity Log and BLT Secure share the gap.
- **`wp option patch update` stores strings, so a setting read with PHP truthiness means the opposite of what was typed.** `"false"` and `"off"` are truthy, and `uninstall.php` used `empty()`, so `delete_data_on_uninstall` set to `false` from WP-CLI deleted everything. `BLT_Toolkit_Settings::merge()` now sends every stored value through `sanitize_field()`, with the default standing in for "the current value" (`read_field()`): booleans through `to_bool()`, integers clamped by `INT_RANGES`, whitelists applied, lists cleaned (which also stops a damaged `usernames.disallowed` from crashing Settings > Usernames). `uninstall.php`, which cannot load the plugin, repeats `to_bool()` inline; keep the two in step. Never read a BLT setting from the raw option with `empty()` or `(bool)`; use `BLT_Toolkit_Settings::get()`.
- **Screens name idle modules from the registry, never by building them.** `BLT_Toolkit_Admin::modules()` used to `new` every module that did not boot just to read `label()`, which loaded code SPEC 4.1 says must not load (and would let a broken module file break the screens used to diagnose it, SEC-15). The built-in names and descriptions now live in `BLT_Toolkit_Plugin::labels()`, which the module classes return too; a new built-in module adds its entry there. A filter-added module that is not running shows its key. The earlier "Also check" verification ran only on requests that render no screen, so it missed this; verify "not loaded" while the screens render.
- **`module_status()` reports `conflict` before `disabled`.** GEN-1 requires the Overview card to name the legacy plugin to deactivate, and the constant's note ("remove it from that constant") was false while the legacy plugin was active. When both apply, the conflict note also names the constant.
- **Correction to "The four Phase 0 filters were flipped to Available" (Docs and migration, above).** Only `blt_toolkit_modules` is applied by a running code path. `blt_toolkit_is_toolkit_admin` and `blt_toolkit_lockout_critical_caps` are Planned (Phase 1) and `blt_toolkit_risky_caps` Planned (Phase 4), with a note that the function applying each already exists. A hook is Available when something calls it, not when the method that would apply it exists.
- **Correction to "PRG notices carry only a whitelisted code plus integer or `sanitize_key()` arguments" (Admin screens, above).** `sanitize_key()` still lets a link spell out words (`err=your-site-is-compromised_call-…`), and `http=200&via=stored` faked a successful Test connection. The result is now carried with `blt_sig`, a nonce whose action contains the values (`BLT_Toolkit_Admin::result_args()`), so only the person who ran the test sees it and no value can be changed. Every other notice code takes no argument.
- **Activation refuses, before touching any role, when the tables or the baseline cannot be stored.** Granting first would let the next activation's baseline record BLT Toolkit's own grants as the "before" state. Every refusal goes through `refuse_activation()`, which also clears `puc_cron_check_updates-blt-toolkit`: loading the main file for the activation already built the update checker, whose `Scheduler` constructor schedules that event at once, and no deactivation hook ever runs for a plugin that never became active. The multisite refusal left that event behind before.
- **The baseline race is closed by inserting, then keeping the oldest baseline.** No lock is held, so nothing can be left stuck. The oldest is always a true "before" copy: each activation stores its baseline before it grants, so a copy read after any grant was inserted after that activation's own, older, baseline.
- **`maybe_upgrade()` runs only on wp-admin screens (not admin-ajax.php), WP-Cron and WP-CLI, and checks that before reading the version option.** When the version was never stored, the option is not in the autoloaded set, so `get_option()` alone is a query on every request, before any retry of dbDelta. Any WP-CLI command runs `maybe_upgrade()`, so `blt-site wp NAME eval …` repairs a schema broken on purpose; break it, then test over HTTP.
- **WP-CLI's `--exec` runs before WordPress loads, so `add_filter()` does not exist there.** Pre-initialize the hook instead: `$GLOBALS['wp_filter']['query'][10]['my_id'] = array( 'function' => $callback, 'accepted_args' => 1 );`, which WordPress turns into a `WP_Hook`. Put it in a file and `require` it from `--exec` or from a `php -S` router, to fail a CREATE or INSERT during activation, or to hold an INSERT for a race test, without an mu-plugin in the shared core.
- **Until Phase 1 lands, screens say protection, hiding, recovery and the log are still to come.** A control that has no effect yet stays on its form, marked with `BLT_Toolkit_Admin_Settings::later()` or a "Coming soon" badge, because `save_tab()` reads a toggle that is not submitted as off. Phase 1 has a todo item to restore the present tense.
- **Docs quote the screen's label, with the settings key, not SPEC's name for the setting.** HOOKS.md and the README's Settings table say **Work with tools made for User Switching** (`switch.compat_hooks`), mentioning SPEC's "Compatibility hooks" only in passing; likewise the uninstall toggle is **Delete all plugin data on uninstall** on the screen and everywhere else.
